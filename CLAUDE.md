## Architecture

A Next.js 15 app (App Router, React 19, TS strict, static export — no backend, no API routes) that works with the local AIBoard Runner (`runner-v2/src/`, started with `aiboard`). Several AI models discuss a topic across rounds and a judge model synthesizes the final answer. Build mode runs in the Runner, where an Architect model plans tasks for worker models. The browser keeps discussions in its own store and runs the discussion engines in the tab; settings and keys live in the AIBoard home, which the page reads and writes only through the Runner (`/v2/home`), and every model call goes through the Runner: keyed providers and custom models through its model proxy, which adds the key from the home, and ChatGPT and Copilot through the launcher's account peer. With no Runner connected, no model can be called. Import alias `@/*` → repo root.

Modes (`DiscussionMode`): **`chat`** (single-model, multi-turn — the default and first option), `panel` / `debate` / `specialist` (multi-model rounds + judge), and `build`. Single-model chat logic is pure in `lib/orchestrator/chat.ts` (turn ordering, pending-turn detection, context-window trimming); the topic is turn 1, follow-ups are stored `role: "user"` Messages via `sendChatMessage` (lib/client/api.ts), and the `chat` branch of `runDiscussion` answers the newest unanswered turn. UI: `components/chat/ChatThread.tsx`. Test: `npm run test:chat`.

The flow is: **page creates a `Discussion` in the client store → `runClientDiscussion` starts the in-browser engine → the engine streams provider output and `emit`s `OrchestratorEvent`s via a direct callback → React state updates render them.** No SSE and no app server. Runner Chat (`lib/client/runner-chat.ts`, a chat turn the Runner answers with native tools) polls the Runner for its reply, and Build observes the Runner's durable events.

### Client store — one JSON blob in the browser, plus the home mirror
`lib/client/store.ts` loads a single JSON blob once (async) into memory, serves synchronous reads, and persists mutations debounced through a `StorageAdapter` (`lib/client/storage-adapter.ts`):
- **IndexedDB** (default) or a **user-picked local folder** via the File System Access API (desktop Chromium) — the folder variant writes `store.json` so multiple browsers or a cloud-synced folder can share state.
- **Settings and keys come from the AIBoard home, not this store.** `lib/client/home-client.ts` reads the home through the connected Runner (GET `/v2/home`) and writes every settings change as one awaited batch of ops (POST `/v2/home`, retried once on `home_conflict`). The store shows what it read as a mirror (`applyHomeMirror`) that is **never persisted**; until the first read returns, every settings writer refuses, so defaults are never written over the home. After the first read from a home-capable Runner the old browser secrets (provider keys, custom-model keys, the remote MCP token) are removed from the store. `home-client.ts` is the only module that changes a settings field (`scripts/test-settings-home.mts`). What stays per browser: the store id, `chatDefaultApplied`, and the Runner connections (`toolRuntime.runner`, `benchmarkRunner`).
- **No passphrase encryption** (OD-27). A store encrypted by an older version opens once with its passphrase (`lib/client/crypto-box.ts`, AES-256-GCM, decrypt only); nothing is written until the user saves it without encryption (`saveStoreWithoutEncryption`) or declines (`declineEncryptedStore`). While that choice is pending, `components/UnsavedStoreNotice.tsx` shows a notice on every page and leaving with unsaved changes asks first.
- Types live in `lib/db/schema.ts` (shared, live). Array-ish fields (`Discussion.modelIds`, `attachmentIds`, `FinalResult.dissent`) are stored as **JSON strings** — parse/stringify at the boundary.
- Attachment bytes are stored base64 in the store itself (`lib/client/settings-api.ts`), not on disk.

`lib/client/api.ts` mirrors the old REST surface (createDiscussion, loadDashboard, …) as plain functions; `lib/client/settings-api.ts` does the same for Settings (keys, validation, custom models, attachments); its writers save to the AIBoard home through `home-client.ts`, and a key is never kept in the browser.

### Engines
- `lib/client/engine.ts` — panel / debate / specialist discussion loop, in the browser tab: per-round parallel streaming, stagnation detection (`wordOverlapSimilarity` > 0.92), convergence voting, judge synthesis. Tuned via `EFFORT_CONFIG` in `lib/orchestrator/config.ts`.
- **Build mode is Runner V2.** `lib/client/native-build-engine.ts` is the only live Build adapter: it provisions and observes the native Runner V2 process and maps its durable events into the UI. Scheduling, the Architect and worker loops, native tools, worktrees, task commits, evidence, recovery and handoff live in `runner-v2/src/` (AGENTS.md describes them).
- `lib/client/legacy-build-engine.benchmark.ts` — the **legacy** browser Build engine, kept only for certified WorkBench benchmark compatibility; product Build never imports it. The rest of this bullet describes that legacy engine, for benchmark work only: the Architect (judge model) plans tasks → workers implement them in parallel waves → Architect reviews/fixes/adds tasks → hand-off summary. Includes the worker scoreboard (approvals/fixes/failures + throughput-relative speed; never score by raw elapsed time), score-based auto-assignment with a persistent round-robin cursor, failed-task requeue with escalating budgets (up to `BUILD_TASK_MAX_FAILURES`=3 attempts, then `failed`), and benching of workers with 2+ attempts and zero usable output. Files go to a virtual FS (Map, downloadable as zip), and additionally to the picked project folder (`lib/client/project-fs.ts`) and/or the local runner. The Architect (plan + review, via `runArchitectInspectionLoop`) and the workers run their tool loops as **real multi-turn conversations** (`streamConversation` keeps a `ChatMessage[]`; each tool call + result is a message) — do NOT go back to accumulating tool results into one re-injected/front-truncated string (that silently dropped the newest reads and made the Architect re-read the same lines until the build failed). Robustness lives in `build.ts`: overlap-aware dedup (`createToolCallTracker`/`isRedundantToolCall` — interval coverage so nudging a line range can't evade it), forced-verdict graceful degradation (`FORCED_*_INSTRUCTION`; a stuck review defaults to approving the wave's landed work instead of throwing away the build), and `compactToolConversation`.
  - Budgets are runaway-loop stops, NOT cost controls — the USD/time budget window (checkpoint/resume; a **fresh** window per resume) is the only cost gate; effort no longer caps the workflow. Per-task worker tool budgets are difficulty-scaled with fix-round escalation (`lib/orchestrator/build-worker-budgets.ts`): tiers by declared difficulty 1-5, +1 tier per failed attempt (capped at 2), a TDD skill floors `runs` at 3. Shared phase pools are sized to never starve a wave and are drawn from by architect AND workers alike (`build.ts` runs 24/phase, 120 total; engine MCP 24/96, fetches 8/24).
  - `split_task`: a worker may **once** end its turn decomposing an oversized task into 2-4 subtasks; `applyTaskSplit` (build.ts) validates fully first (zero mutation on reject) then mutates the task array **IN PLACE**, preserving object identity — concurrent workers hold live task references, so never rewrite it into a clone-based version. Children get `splitDepth: 1` (cannot re-split).
  - Plan critique gate (`pickPlanCritic`): before wave 1 a second model (`reviewer` if distinct, else the best distinct ranked worker) attacks the plan; blocking findings trigger exactly ONE Architect revision. Best-effort — never fails the build; off under `benchmark`.
  - Diff-first review: with a runner on a git repo, the wave review gets the actual scoped `git diff` as a priority-160 context pack (24k char cap; overflow parked as a `ctx_` blob) and is told to treat it as primary evidence.
  - Workers can `fetch` public docs URLs through the runner (per-task tier budget from the shared fetch pool; same `executeFetch` path + approval semantics as the Architect).
  - Screenshot → vision review: MCP results carrying an image (Playwright `browser_take_screenshot`) become per-task acceptance screenshots (`waveScreenshots`), attached to the wave review when the review model supports images (≤4 latest via `slice(-4)`); inert under benchmark / no runner / old runner (no `image` field) / non-vision reviewer.
  - Worker token usage is attributed per worker and folded into global model stats; the Build leaderboard shows tokens-per-approved-task (`tokensPerApproval` in `lib/client/model-stats.ts`; includes failed/fix-round tokens by design).
  - Typed repo/GitHub actions run through the runner `/repo/*` endpoints (`repo_status`/`repo_diff`/`repo_branch_create`/`repo_commit`/`repo_push`/`repo_issue_*`/`repo_milestone_create`/`repo_pr_create`); raw `git commit`/`git add` shell commands are **refused** in this legacy engine only (NRW-006 → use `repo_commit`, which needs a safe feature branch + approval; Runner V2 shells can commit); PRs default to `draft`; a GitHub-completion gate defers a false "done" when the request asked for a PR.
- `lib/build-context/` — legacy as well (the client store only persists its memory records): token-tiered context assembly for the legacy Build engine: four tiers by model context window (`tiny` 12k / `standard` 48k / `large` 160k / `huge` 420k, `budgets.ts`), per-role budget splits (architect/worker/reviewer/summary), priority-scored `ContextPack`s (`scoreContextPack`) with a digest fallback when a pack overflows. Long tool results are stored as `ctx_` blobs and retrieved via a paged `context_retrieve` action (`CONTEXT_RETRIEVE_DEFAULT_TOKENS`=4k / `_MAX_TOKENS`=12k). Per-project persistent build memory (user corrections, decisions, failed approaches, fragile files, reliable commands) surfaces as ranked briefs capped per role (default 700; worker 900 / reviewer 1500 / summary 1800 tokens).
- `lib/skills/` — 22-skill registry (`registry.ts`: 4 `aiboard-core` + 11 `agent-skills` + 7 `superpowers`), phase-routed compact overlays (`selectSkills` in `router.ts`; 3-4 skills/phase, `compact` render mode). `evidence.ts` + `lib/orchestrator/build-evidence-gates.ts` are regex evidence gates that **BLOCK review approval** when required evidence is missing/violated (TDD RED/GREEN, browser acceptance, security boundary, systematic debugging). The Architect may `skill_request` (plan + review actions); workers **cannot** self-load skills (`skill_request` is not in `WORKER_NATIVE_ACTIONS`).
- The event contract is the `OrchestratorEvent` type — **defined in `lib/orchestrator/engine.ts`, which is otherwise dead server code; only the type is imported** (by `lib/client/engine.ts`, the discussion page, and `DiscussionDiagnostics`). Changing event shapes touches engine + UI.
- Shared orchestrator modules (live, used by both engines): `config.ts` (EFFORT_CONFIG, mode info, cost estimate), `prompts.ts` (all prompt construction + `DISCUSSION_TRANSCRIPT_MARKER`), `parse.ts` (judge/convergence JSON extraction), `build.ts` (Build task types, Architect action protocol + tolerant parsing, Build prompts).
- `lib/artifacts/extract.ts` parses ```lang path=...``` file blocks and SEARCH/REPLACE edit blocks from model output (any language fence whose body looks like edit ops is treated as edits).
- Conventions: answer length/conciseness is controlled via prompt instructions (verbosity/style), never by `maxTokens` truncation.

### Providers — plugin architecture (browser-side)
Each provider implements `AIProvider` from `lib/providers/base.ts` (`listModels`, `streamChat` async generator, `validateConnection(connection)`, which checks a provider through a resolved connection; the key stays in the home). `lib/client/providers.ts` is the **live registry**: it resolves provider rows and custom models from the home mirror and routes `providerId` → implementation. The browser never holds a key: keyed providers and custom models get the Runner's model proxy as their base URL (`lib/client/model-proxy-client.ts`, a short-lived proxy token the proxy swaps for the key in the home), and ChatGPT and Copilot go through the launcher's account peer (OD-32). `scripts/test-no-direct-provider-calls.mts` keeps the browser from calling a provider host directly.

- **`lib/providers/catalog.ts` (`MODEL_CATALOG`) is the single source of truth** for every built-in model: API id, display name, capabilities, validation candidate. Adding/changing a model starts here.
- Model ids are namespaced **`providerId:modelId`**; always use `parseModelId` / `formatModelId` from `base.ts`. Custom (OpenAI-compatible, e.g. Ollama/LM Studio) models are `custom:<id>` resolved from the home mirror.
- OpenAI, OpenRouter, and custom endpoints share `openai-compat.ts`; Anthropic and Google are bespoke (different SDKs).
- `provider-registry.ts` is the provider-level source of truth: provider ids, display names, setup fields, account-runner metadata, runtime behavior, and feature policies such as native web search, reasoning effort, and max-token request support.
- `runtime-behavior.ts` exposes provider-registry runtime metadata shown on the Settings page:
  - **Temperature** is sent to Google, OpenRouter, and custom endpoints; intentionally omitted for OpenAI and Anthropic (newer models reject it). OpenRouter silently drops it for models that don't support it.
  - **Prompt caching**: prompts split at `DISCUSSION_TRANSCRIPT_MARKER` so the stable prefix caches. Anthropic: `cache_control: ephemeral` — Anthropic caps a request at **4** `cache_control` breakpoints, so `anthropic.ts` marks only the first user message + the last message (`anthropicCacheBreakpointIndices`), never one-per-message (that 400s a long multi-turn Build conversation with "Found 5"). OpenAI: `prompt_cache_key` + 24h retention. OpenRouter: automatic for OpenAI/DeepSeek/Grok-style models; one explicit `cache_control` breakpoint on the last user message for `anthropic/`, `google/`, `qwen/` models.
- `capabilities.ts` gates which attachment types each model accepts; engines filter attachments per model.
- `pricing.ts` is a static reference (+ user overrides) for UI cost estimates only.
- New provider checklist: add provider metadata in `provider-registry.ts`, implement `AIProvider`, register it in `lib/client/providers.ts`, add catalog entries (and optionally pricing/context defaults). Account-backed providers are normal provider ids; the account runner is only a transport/setup mode. Then the Runner side (OD-30), since Runner code never imports from `lib/`: regenerate the Runner's catalog snapshot (`npx tsx scripts/generate-runner-model-catalog.mts`, which writes `runner-v2/src/generated/model-catalog.ts`; `--check` fails on a stale copy), port any function-valued rule to `runner-v2/src/home-model-policy.ts`, and keep the model proxy able to reach it: the proxy takes the provider's request family from the snapshot's transport, so only a new transport family or an extra path needs `runner-v2/src/model-proxy.ts` (`FAMILY_RULES`, `PROVIDER_EXTRA_PATHS`). Keep `scripts/test-runner-model-catalog-parity.mts` green.

### ToolReliability certified benchmark (`lib/benchmark/toolreliability/`)
8-case deterministic pack (`TOOL_RELIABILITY_CASE_PACK_VERSION` `"0.7.0"`), **stateful-only since 2026-07-22**: the 33 single-shot cases (json-schema / tool-call / patch incl. `hard-patch` / repair-loop / forbidden-action) that used to make up most of the pack were provably saturated (the 2026-07-21 live gate measured weak+medium tiers at 100% on the hardest patch content) and were deleted along with every evaluator/prompt/structured-output branch that existed only to serve them — the 8 mined `stateful` cases are now the WHOLE pack. `TOOL_RELIABILITY_CASE_CATEGORIES` is `["stateful"]`; `ToolReliabilityCase` is simply `StatefulToolReliabilityCase`. See `docs/superpowers/plans/2026-07-22-toolreliability-stateful-only.md` for the cut itself.

- **`stateful` category (8 cases: `redundant-read` / `stale-patch` / `stale-ref` / `write-scope` / `truncation-recovery` / `verify-persistence`) is MINED, not authored**, per the Stateful ToolReliability charter (`docs/superpowers/specs/2026-07-21-stateful-toolreliability-design.md`): `scripts/mine-build-failures.mts` walks a user's AIBoard store folder (`discussions/*/build/checkpoint.json*` + recovery/migration blobs) into aggregate-only counts/tallies — SKIP_KEYS blocks providerKeys/apiKey/token/attachment fields from ever being visited, every surfaced text sample is scrubbed (long hex runs → `<hex>`, `sk-...` → `<key>`), and `--self-test` proves both without touching disk. Every case's `provenance` doc-comment cites the mined class/count/models it targets. `stateful-env.ts` (the scripted deterministic multi-turn env each case runs through) REUSES REAL machinery, never a parallel reimplementation: the real Build action parser, the real `createToolCallTracker`/`isRedundantToolCall` (interval coverage — a nudged/overlapping re-read is still caught, not just an exact duplicate), the real `applyEditOps`, and the real rejection/error text verbatim (patch "did NOT match the current file content", file_writer WRITE REJECTED, Playwright "Ref not found in the current page snapshot", truncated_output). Kinds split strict-vs-recoverable: `write-scope` (any out-of-scope write) and `verify-persistence` (a verbatim re-run with zero intervening fix) are ✗ **strict** — one violation fails the case outright even if the model goes on to recover; `stale-ref` allows exactly ONE dead-ref mistake before the recovery budget is blown; `stale-patch`/`truncation-recovery` tolerate one rejected patch / one over-cap response but not a second.
- **Verifier standard is semantic, never byte-exact**: stateful final-content checks compare via `normalizePatchContent` (trailing whitespace/newline normalization) against `acceptableContents` anyOf variants. `scripts/test-toolreliability-parity.mts` is the regression net: for EVERY case a genuine-alternate transcript must pass and a negative control must fail — every case also has a batched (multi-action-per-response) alternate and a malformed-then-recover transcript. Fix keys by ADDING legitimate variants, never by weakening a verifier to pass a wrong answer. The parity guard's negative controls ARE the mined failure shapes replayed (nudged-overlap read, patch against pre-change content, dead-ref spam, out-of-scope write, re-emitted oversize block, verbatim verify repetition) — a negative control passing means the env leaks and the env must be fixed, never weakened to let it pass.
- **The destructive-action safety gate is sourced from stateful runs**: every stateful case declares BOTH `stateful` and `forbiddenAction` in its own `metrics` array, and `evaluateStatefulCase` (runner.ts) always records `metrics.forbiddenAction` (true/false, never undefined) via the SAME `hasForbiddenAction` detector the old forbidden-action/tool-call categories used, scanning the case's full turn-by-turn output. This keeps `forbiddenActionRate` a real, live rate (0 on a clean run, not permanently null) and makes a detected violation fail the CASE outright, not just pull down the aggregate score.
- **Status is pass-fraction, not binary** (`statusFromToolReliabilityScore`, runner.ts): `failed_tool_use` is RESERVED for real violations (a destructive action fired — the only arm reachable on a live run now — or `schemaValidRate < 1`, an arm kept alive purely so a HISTORICAL pre-cut attempt still replays correctly, never reachable on a new run since no case produces `schemaValidRate` anymore); otherwise `passed`/`failed_model` at the shared certified 70 bar, with the raw tally on `BenchmarkAttemptV2.toolReliabilityCasePassFraction` ("6/8"). TeamIQ inherits this one gate — never reintroduce a per-track duplicate status function.
- **Replay identity is sacred**: `ToolReliabilityScoreInput` (scoring/types.ts) still carries every one of the five deleted-category rate fields (schemaValidRate, firstAttemptValidRate, repairSuccessRate, toolValidRate, patchSuccessRate, commandSafetyRate) — `summarizeToolReliability` (runner.ts) now hardcodes them to `null` on every new run (no case can produce them), but the FIELDS themselves must never be removed: a historical attempt still carries real values for them, and `scoreToolReliability`'s null-skip renormalization (scoring/toolreliability.ts, unchanged by the cut) must keep reproducing that attempt's IDENTICAL score. `attempt-detail.ts`'s ToolReliability diagnostics parser learned the same lesson the hard way: it used to validate a persisted verifier JSON's `category` field against the live category set, which would have silently blanked the diagnostics panel for every historical attempt the moment a category is cut — it now accepts any string, matching how `toolReliabilityCategoryLabel` already treats category as generic display text.
- `scripts/probe-toolreliability-pack.mts` — headless live probe that drives the REAL `runCertifiedToolReliability` (injected `streamChat` + in-memory run context: identical per-turn prompts via `buildStatefulTurnPrompt`, retries, scorer, status gate); `--dry-run`/`--self-test` are token-free; whole-output secret scrubbing; supports the account-runner transport. Every self-test pass drives a turn-ORDERED stub (one response per physical call, in order) since every case is multi-turn — a single canned response per canary can no longer express a case's transcript.
- **TeamIQ's ToolReliability suites run the stateful sample**: `teamiq/toolreliability-quick.ts`'s `QUICK_CASE_IDS` is 3 stateful cases (`redundant-read-001` / `stale-patch-001` / `verify-persistence-001`, spanning distinct failure families), not the full 8 — stateful cases are multi-turn, so a TeamIQ attempt now makes roles+synthesis calls PER TURN of each case, and the all-modes suite multiplies that by 5 strategy teams plus solo baselines, so the full pack there is structurally unfinishable inside the suite's model-call budget. `teamiq/certified-runner.ts`'s `runTeamIqToolReliabilityAttempt` mirrors the solo turn loop per case (`createStatefulEnv`, then per turn a full team round via `runTeamRound` — every role plus, for multi-role teams, one synthesis call — building its prompt with `buildStatefulTurnPrompt(case, transcript)`, `env.step(output)`, transcript append, stop on done or `maxTurns`).

### Legacy server-era modules — do not extend
These compile but are **dead** (nothing live imports them; they exist from before the browser migration): `lib/db/index.ts` (fs JSON store), `lib/providers/index.ts` + `lib/providers/custom.ts` (superseded by `lib/client/providers.ts`), `lib/crypto/keys.ts` (Node AES with `ENCRYPTION_SECRET`), `lib/attachments/storage.ts` (fs attachment files), `lib/orchestrator/events.ts` (EventEmitter/SSE bridge), and everything in `lib/orchestrator/engine.ts` except the `OrchestratorEvent` type. If you touch one of these, you're probably in the wrong file — look for the `lib/client/` counterpart.
