The event-driven design and the fusions are mostly sound. Every durable fact survives except one binding link (N1, not blocking). ## Answers to the five questions

**1. The three fusions.**

- (a) Terminal fusion. Old: reattest (birth vs the binding, exited), then the terminal read (processId, stopped, released), then reattest again. New: one read that checks processId, `startedAt`, stopped, released. `processId`, stopped and released are enforced as before. The birth check changed target: the old reads compared the record with the binding (`identity.startedAt`); the new one compares it with the `startedAt` in the attach snapshot. The evidence and the code comment say that snapshot is "taken after the acquire reattest proved the binding birth". That is true for the split path only. In the fused path the snapshot is taken inside the fused effect, before `authority.reattest()`. So the chain is: attach snapshot = X, reattest proves record = binding at a later time, terminal read = X. It holds unless the record is rewritten and rewritten back. The binding compare still runs in the loop reattest right before the terminal read, at observe-final for one-shot calls, and in the release fence (`expectedStartedAt`). The dropped "still exited after the read" is safe because supervisor terminal state is monotonic. Verdict: information survives except the binding link next to the terminal read. That is a partial weakening that should be recorded as an owner decision (N1). Not a blocker on its own.
- (b) Claim + attach. It is one lock hold and one fence effect, not one durable transaction: there are two atomic record writes (the fence CAS, then the status apply inside attach). The predicates are the claim predicates and then the attach predicates, in the old order (I compared the fused body line by line with `claimOwnedFence` and `attachOwnedChannel`). It is stricter than before, because nothing can interleave between claim and attach. A crash between the halves leaves the same durable state as the old crash after the claim effect. Probe H: the attach half throws after the CAS persisted; on-disk fence is token 2; a new host instance rejects token 1 and accepts token 2; PX-2a (split path) and PX-2b give identical output. No test pins this (N4). One order change: the acquire order is now claim+attach, then reattest, where history was claim, reattest, attach. The attach observation now runs on a record whose birth is not yet re-verified. The result is withheld when reattest throws, so nothing escapes. Deleting that reattest is not caught by any new test (B2, fault F5).
- (c) Release. The dropped pre-lock re-read is covered by the in-lock `final` read with the same predicate and the same message. Probe D (real host, `beforeFenceEffect("release")` to change state after the pre-checks): a newer fence written after the pre-checks gives "writer fence is stale", no tombstone; a status flipped to live gives a rejection, no tombstone; the control run releases. PX-2a and PX-2b behave identically. A stale writer cannot release. The guard is not pinned by a test (B2).

**2. Event-driven waits.**

- `GET /wait-status`: it goes through the same `authorized()` gate as every route (timing-safe Bearer compare against the per-call token), so the scope is the same. Real-supervisor test D4 checks 401 for a forged token and 200 for the real one. It is per call (one supervisor and one token per call) and returns exactly what `/status` returns. It mutates nothing. The host method checks record ownership (runId, sessionId) and the current fence, and runs outside the fence lock, so it cannot block ACKs. Bounded: server clamp 1-5000 ms, client sends at most 1000, request timeout bound + 250 ms, waiters clean themselves up. There is no cap on concurrent waiters, but each needs the token.
- Lost wakeup. The terminal case is safe: the check and the registration run in one tick, so a terminal state that lands before the GET returns at once, and one that lands after wakes the waiter (every transition to `stopped` goes through `persistStatus`). A non-terminal change is not safe: there is no cursor, so a change that lands after the caller's last read is not reported (N2, probe G: an output change at about 1.0 s, a wait started at 1.6 s parked the full 1.5 s and returned after 1520 ms). Cost is bounded by the 1000 ms cap and the remaining settle deadline, so it is latency, not a hang.
- The startup wait loses wakeups and its fallback is the whole deadline (B1).
- Deadlines: the settle expiry race, the `Math.min(1000, remaining)` cap, the start deadline and the call-level stop path are all still armed. `waitForTerminal` never had its own deadline.
- Backward compatibility: an old supervisor answers `/wait-status` with HTTP 404, the host throws, and the channel falls back to `delay(25)` (probe E).

**3. Crash recovery and old records.** No durable schema changed (`HostRecord` and the supervisor status line are untouched). Probe E: launch with the PX-2a code (old record, old supervisor with no `/wait-status`), then take over with the PX-2b code at fence token 2. `waitOwnedStatusChange` throws `HTTP 404`, the fused CAS upgrade is accepted, `observe` returns `exited`/0 with stdout `old-ok\n` after 5.5 s, `verifyEmpty` is empty, `release` succeeds. The other new boundaries are read-only (terminal read, both waits) or unchanged (release tombstone write).

**4. Tests.** See B2 and N5. The two guard files pass 16/16 on the pristine commit and are byte-identical to the parent (checked). The 14 new tests pass 14/14. Most pin the helpers and the happy path; none can see a weakened proof.

**5. Hidden weakening.** See the table at the end. The brief's list, item by item: fewer re-attestations of birth: yes, from 5 binding compares per call to 3 plus one snapshot compare (N1, not listed by the worker as an owner decision); fewer fence checks: no (the durable fence check still runs in every effect; only the backend's in-memory pre-check ran fewer times); a removed audit fact: no.
