## The three faults that stayed green

The worker calls this "layered defense". I checked each one in a scratch copy.

1. **`process_start_failed` swallowed** (`windows-job-process-host.ts:198`). **A later layer really catches it.** With the throw removed, the call still ends `threw: Process launch was not proven.` (same message as the pristine run, one Job record). Where: the failed launch never gets a child PID, so the host record keeps `pid: 0`. `parseProcessLaunchResult` requires `rootPid` of at least 1 (`process-backend.ts:291`, `integer(o.rootPid, 1)`). The runtime turns the parse failure into "Process launch was not proven" (`subprocess-runtime.ts:740-771`). This layer is not tied to the PX-2 changes. Acceptable. Note the test regex `/launch_failed|threw/` accepts any throw, so it would also pass for an unrelated error (F6).
2. **Always-true `verifyEmpty`.** **A later layer catches it in production, but no test pins either layer. This is a hole for PX-2b (B2).** Layer: `releaseOwned` refuses unless the supervisor says `stopped` and `ownershipReleased` (`windows-job-process-host.ts:247-253`, twice). Probe: with the fault and a live descendant, `backend.release` throws `Windows Job process ... is not verified terminal.` (and leaves the control lane closed, so it cannot be used inside a test that must still kill the tree). The runtime turns that into `backend_release_failed` and cleanup `failed` (`subprocess-runtime.ts:1082-1098`). So a single change to `verifyEmpty` or to `release` is safe today. But PX-2b wants fewer effects, and `verifyEmpty` (one reconcile effect) and release's second `authenticatedStatus` read are the obvious cuts. Each single cut looks harmless and nothing would notice the second. The test that detects it: the backend-level control in B2(a) (my probe: red on the fault, green on pristine). It is blocking for PX-2t because it is cheap (the T7 harness exists, about 40 lines) and PX-2b is next to change this path.
3. **Recovery "cleaned".** **A hole, and the matrix overstates it (B3).** `recover()` returns empty lists in the T12 scenario, so no recovery logic runs.

## Question 4: host death reports `exited` + `verified_empty` and no exit code

The finding is right. When the Job-host process dies, the supervisor's `exit` handler sets `jobEmptyProof` (`managed-process-supervisor.mjs:273-277`). `close` then calls `tryMarkStopped`, which calls `markStopped` (`:278-290`, `:427-436`). The exit code is set only by the `natural_stopped` event (`:406-409`) or in the not-proven branch (`:290`). So `stopped` with `exitCode: null`. The backend maps it to `exited` without `exitCode` (`windows-process-backend.ts:154,173`). My probe: `exited verified_empty exitCode: undefined`.

Downstream, what I read:
- Git fails closed: `git-runtime-runner.ts:58` requires a safe-integer exit code.
- Delivery, evidence and final verification map null to `unknown` or not green (`delivery-execution.ts:675`, `delivery-acceptance.ts:99`, `final-verification-semantics.ts:183`, `final-verification-runtime.ts:755,836`). `runtime_smoke` tolerates null but also needs readiness and cleanup proof (`:964`, `final-verification-semantics.ts:187-190`).
- One note: the `process.run` tool returns `isError: false` with `exitCode: null` (`process-tools.ts:167-196`), the same as for any completed command. A model reading only "no error" could take it as done. The data says `null`, so this is not a mistake by code, but the outcome name `exited` is generous for a killed host.

No code treats it as verified success. Product follow-up (not PX-2t): report a distinct outcome for "host died before reporting an exit".
