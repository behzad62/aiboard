## Input type and why each field exists

`HandoffSnapshotInput` in `runner-v2/src/handoff-snapshot.ts`
(adapter: `handoffSnapshotInputFromProjection(projection, facts)`):

- `runId` — from `SchedulerProjection.runId`. Identifies the run in headers
  and in every truncation marker (`N more — see AIBoard run <id>`).
- `revision` — from `integrationRevision`; `"not recorded"` when absent (no
  integration yet). The header names the exact revision the snapshot
  describes.
- `stopKind` (`completed | plan_only | paused | failed | answered_export`) —
  derived from real fields only: `runPolicy === "plan_only"`; the
  triage-answer path (`planningPolicyVersion === 1` and
  `planningTriageDecision === "answer"`); else `status` with `pauseReason` /
  `failureReason`. No other stop taxonomy exists in the projection.
- `stopReason` — `pauseReason.reason/detail`, `failureReason`, handoff
  status, or `"not recorded"`. Nothing else records why a run stopped.
- `stopAt` — caller fact (`HandoffSnapshotFacts.stopAt`); the projection
  holds no stop timestamp, so without it the renderer prints
  `"not recorded"`.
- `sourceTitle` / `sourceDigest` — from
  `planning.source.manifestsById[currentManifestId]` (`sourceId` /
  `artifactDigest`). Manifests carry no title field, so `sourceId` stands in
  for the title (documented in the adapter).
- `specPath` — caller fact; no spec path exists in the projection.
- `requirements?` — from `ledger.requirements`, else the current plan
  revision's requirements; absent when neither exists, which selects the
  task-list rendering. Status: `not_applicable` / `conditional_pending`
  straight from `applicability` (reason = disposition rationale +
  authorizedBy, or the condition expression); otherwise `accepted` iff a
  `delivery.phaseAcceptances` record names the id (the only durable
  requirement-level acceptance), else `open`. Outcome one-liner =
  `observableOutcome`.
- `tasks` — current revision tasks (`outcome.user`), else scheduler tasks
  (`objective`); accepted iff a `delivery.taskAcceptances` record names the
  id (scheduler tasks: `integrated` status). Feeds open work and the
  no-ledger task list.
- `openFindings` — every `delivery.reviews` finding with
  `severity === "blocking"` and no disposition (the same rule as
  `openBlockingFindings` in `delivery-acceptance.ts`, inlined so the module
  keeps zero runtime imports beyond `node:crypto`).
- `externalBlockers` — `repairIssues` entries with `externalBlocker`
  (owner action + acceptance condition).
- `exhaustedRepairIssues` — `repairIssues` with `used >= limit`.
- `verification` — `finalVerification.current.completedChecks` (exact
  command from command facts; `executed/failed` from the command fact
  report; `"not recorded"` when absent) plus the latest
  `delivery.boundaries` record per task (tests-check report counts).
- `decisions` — current revision `planningDecisions` (`id: description`)
  plus acknowledged owner guidance (`userGuidance` with status
  `acknowledged`).
- `notes` / `notesAbsentReason` — `projectHandoff.summary` (the
  `complete_run` summary); otherwise the slot prints
  `No Architect notes for this stop: <reason>`.
- `nextAction` — derived: failed → inspect; paused → resume; blocker →
  owner action; completed → handoff choice; plan_only → review plan;
  answered → nothing to do.
- `plan?` — present for plan-only stops: phases (purpose, contributing
  tasks, exit criteria) and tasks (outcome, phase, dependencies, steps,
  acceptance criteria) from the current revision.

## Body-digest rule (for C2 hand-edit verification)

The output is `firstLine + "\n" + body` where `firstLine` is
`# AIBoard handoff snapshot — body_sha256: <hex>`. `<hex>` is the lowercase
hex sha256 over the UTF-8 bytes of everything after the first newline, i.e.
over `output.slice(output.indexOf("\n") + 1)` — the body below the header
line that holds the digest, trailing newline included when present. C2
recomputes the digest over that exact substring. Any hand edit below the
header changes the digest. `verifyHandoffSnapshotDigest` implements the
check; the golden fixture digest is
`8383950441c7f86933d1680c3e01c38d2b8ff98ffd0dbd4310fcf54cf05b1fb6`
(independently recomputed with a plain `node -e` sha256 one-liner: match).

Neutralizing rules: `<!--` → `&lt;!--`, `-->` → `--&gt;`, C0/C1 controls
(except `\n`, `\t`) removed, every field capped (500 chars; notes 2000),
table cells additionally `|` → `&#124;` and newline → `<br>`. All lists are
sorted (insertion-order independent). Truncatable lists (requirements, open
tasks, non-blocker findings, exhausted issues, decisions, plan view) shrink
with `N more — see AIBoard run <id>`; header, external blockers, open
blocking findings and verification never truncate.

## Not done / limits

- Wiring the renderer into the runtime is packet C2 (named wiring packet);
  this module has no callers yet by design.
- Bounds guarantee: truncatable lists shrink until output fits 200 lines /
  16 KiB, but header, external blockers, open blocking findings and
  verification never truncate — a pathological input with hundreds of
  verification entries or blockers could exceed the caps. Realistic runs
  (incl. the 120-requirement / 60-task stress test, which fits) are far
  below that; each entry is field-capped.
- `stopAt`, `specPath`, exact build/test commands beyond what boundary and
  final-verification records hold, and the notes-absent reason override are
  caller-supplied plain-data facts because the projection does not hold
  them; missing values render `"not recorded"` and the adapter test asserts
  exactly that.
- Requirement `accepted` status requires a phase acceptance naming the id;
  task-level acceptances alone do not accept a requirement (matches the
  schema: only phase acceptance carries `requirementIds`).
- `answered_export` rendering is covered at input level only; no answered
  run was seeded through SQLite in this packet.
