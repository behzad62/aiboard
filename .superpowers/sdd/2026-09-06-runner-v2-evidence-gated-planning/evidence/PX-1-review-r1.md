## Answers to the five questions

1. **Call path (§1).** It is the path git takes on Windows. `createExecutionHost` puts `runner-windows-job-v1` first and the probe read `managed-processes-job-host`. The launch and settle part is complete and the file:line cites I sampled are right. Two small differences: the probe uses `withCall/current` (`git-run-context.ts:82-93`), while `IntegrationManager` uses `lifecycle("integration")` (`native-build-factory.ts:651`, `git-run-context.ts:125-166`). I measured the difference: +6 ms, so it does not matter. And the report says 934 ms "reproduces" the controller's 1,014 ms; it is 8% lower, still fine. Process list gaps: `csc.exe` and `cvtres.exe` (from `Add-Type`) are started on every call and are missing from §1. "Measured: exactly one of each" is only measured for the node supervisor (the probe wraps host-side `spawn`); the PowerShell and git counts come from reading code. The ps1's own 25 ms loop (`managed-process-job-host.ps1:301`) is missing from the wait list. Only `permissionProfile: "full"` was measured.
2. **Numbers (§2).** Plausible and consistent, and I reproduced them. Two caveats on method, neither changes the conclusion. (a) The timeline phases tile the whole call by construction (each phase ends where the next starts), so "unexplained remainder < 2%" is a property of the method, not evidence that each phase is understood. (b) The cross-check "launchOwned 483 ≈ 37 + 48 + 18 + 384" adds the pre-spawn 37 ms, which is outside `launchOwned`; the real gap (33 ms) is host poll latency and status GET. The "SQLite exec 173 ms / 166 execs" counts only `exec()`; it misses 33 DB opens and prepared statements. The real cost of the fenced effects is the 14 x ~23 ms above. The three "top sinks" overlap (reconciles sit inside both drain and tail) and cannot be added.
3. **Guarantees (§3).** Incomplete and partly mis-mapped. See findings F1, F3, F6.
4. **Recommendation (§4-5).** A per-run broker as written does not keep every guarantee. See the coverage table and F1-F4.
5. **Side observation.** Real, and I found the cause. See F7.

## Findings

| F1 (material) | **The broker as written reuses one Job across calls. That breaks per-call kill and per-call empty proof.** §4 option 1 says "spawns inside the existing Job"; §5 says "Job reuse across calls" and keeps "empty-proof-before-release exactly as-is". | Production always launches the host in interactive mode (`windows-process-backend.ts:117`). In that mode a per-call timeout works like this: `stopTrigger` -> `backend.signal` -> `signalOwned` -> `/signal` -> the supervisor kills the Job-host PROCESS (`managed-process-supervisor.mjs:461-481`), and that process exit closes the kill-on-close handle. The exact-empty proof is that same exit plus pipe EOF: "Process exit closes the Job host's kill-on-close handle ... That is the exact empty proof" (`:273-277`, `:358-372`; test `windows-job-supervisor-input.test.ts:36`). Chain: `subprocess-runtime.ts:1959-2012`, host `:208-228`. So one host process = one Job = one kill switch. With a shared, long-lived host there is no per-call kill switch and no per-call exit, so neither kill nor proof can be "as-is". (`TerminateJobObject` + `ActiveProcesses` exist in the ps1, `.ps1:448-476`, but only for the non-interactive stop path that production does not use.) Also `git` can leave descendants (`root_exited` case, `.ps1:400-404`); in a shared Job they would leak into the next call's emptiness. | The 1 s cost is only worth removing if per-call timeout kill (a stated guarantee: `verified_empty` after timeout) still works. Say exactly what replaces the process-exit proof (per-call `ActiveProcesses==0` event plus per-call handle/pipe closure). Keep suspended-create -> assign -> resume (`.ps1:368-378` interactive, `:229-240` non-interactive). |
| F2 (material) | **Broker lifecycle is not covered: crash, hang, recovery after a runner crash, run end.** | Today supervisors are `detached` and `unref`'d on purpose (`windows-job-process-host.ts:160-164, 204`); a dead runner leaves the call running and recoverable by adoption (records hold pid, port, token: `HostRecord`, `:76-86`). Recovery is per process (`subprocess-runtime.test.ts:2765, 3251`). The report says nothing about: who adopts or kills a run-scoped broker after a runner crash; a hung broker (today one hung host stalls one call, then it would stall every call in the run); a broker crash (today one call fails closed, then all in-flight calls fail together); end of run (`binding.close` must prove no broker, supervisor or PowerShell is left); idle timeout; orphan reaping. The Job host is shared by all runs of the host (`execution-host.ts:208-211, 261`) and by streaming/LSP (`windows-process-backend.ts:117` always launches `interactive: true`). The backend attests `crash_cleanup: "enforced"` (`:99-104`) and binds a static code identity (`execution-host.ts` `runner-windows-job-adapter-v1`), so a new protocol needs a deliberate identity and compatibility decision. | These are exactly the failure modes that the fail-closed design in CD-20's "every guarantee" protects. A single point of failure per run is a new risk, not a detail. | A written lifecycle: spawn point (bind or first call), owner and parent-death rule (broker dies when its controller pipe closes, or is adopted by a defined protocol), watchdog and restart with in-flight calls failing closed, end-of-run teardown with proof, idle timeout, startup orphan sweep. Keep old per-call records recoverable, or retire them explicitly. State the blast radius. |
| F3 (material) | **Concurrency, output attribution and spawn authority are not addressed. The test gate only covers "two sequential children".** | (a) Concurrency: the run binding is shared by integration, workspace, verification, worker inspection, evidence tools and `process.run` (`native-build-factory.ts:641-762`, `native-worker-driver.ts:498`, `evidence-tools.ts:157`). `IntegrationManager` serializes only its own calls (`integration-manager.ts:2984-2996`). The C# host runs exactly one child (`Run`/`RunInteractive`, `.ps1:183-425`); a broker needs a multi-child loop and per-call event framing. (b) Output: today each child inherits the host's own pipes, drained by one supervisor into a retained window of 16 chunks / 256 KB with ack (`windows-job-process-host.ts:130-132`, supervisor `:307-356`), so a flooding child is throttled by the pipe. A broker needs per-child pipes with the same backpressure. Falling back to per-call log files (the existing `Run` mode) gives easy attribution but no backpressure: unbounded disk. (c) Authority: today the launch config arrives once over the private stdin pipe (`windows-job-process-host.ts:184-195`); the HTTP endpoints can only control a call that is already running (`managed-process-supervisor.mjs:118-207`). A run-wide HTTP bearer token that can spawn would let any local reader of that token start processes. | These are the guarantees "output bounds" and "no ambient authority" from the owner's list, at the transport level. §3 only lists the Node-side caps (4 MB / 128 MB). | Spawn stays on a private pipe or IPC channel; HTTP only controls launched calls; per-call token or check. ## Conditions PX-2 (the fix packet) must meet

1. **Cheap steps first, measured after each.** Order: cached digest-pinned assembly; keep-alive fix; fewer re-attestations and event-driven settle; warm spare pair; only then a multi-call broker. Each step keeps the same probe (n >= 20, quiet machine) and reports fence effects per call.
2. **No Job reuse across calls.** One Job per call, KILL_ON_JOB_CLOSE per call, suspended-create -> assign -> resume kept. Define the new exact-empty proof in writing.
3. **Concurrency is in scope.** Two calls at once in one run must work, including one killed on timeout while the other finishes.
4. **Output stays bounded.** Per-call pipes with the same retained-window backpressure; no unbounded log files.
5. **Spawn authority stays private** (stdin or IPC from the runner). HTTP control only for launched calls. State who can read tokens.
6. **Lifecycle written and tested:** parent death, hang watchdog and restart, end of run (zero leftover processes), idle timeout, orphan sweep, recovery after a runner crash (fail closed, no relaunch), old-record compatibility and adapter identity.
7. **Real-host tests, not mocks,** for every guarantee in the corrected list (F6), including host-death -> tree-death, surviving descendant, output flood, and attribution. Name them in the packet before code.
8. **Acceptance number from measurement.** Measure the per-effect fence-lock floor first. If 200 ms is not reachable without weakening the fence protocol, say so and let the owner choose.
9. **All users of the backend stay green:** git, `process.run`, verification and evidence commands, streaming/LSP (`interactive: true`). Re-run the Windows Job suites (`windows-process-backend`, `windows-job-output-replay`, `windows-job-supervisor-input`, `one-shot-command-family-production-matrix`, `execution-host`, `subprocess-runtime`, `durable-process-store`) after each step.
10. **Measure the production entry point** (`lifecycle("integration")`, a non-`full` profile, no-output and large-output commands), not only `withCall`.
