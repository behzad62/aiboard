# Remote MCP tool surface

Revised 2026-10-27 for owner decisions D15–D17. Updated 2026-11-07 after the Ledgerline benchmark: `git_commit` and `browser` left the surface, results got smaller, and command output became searchable.

## Status

Proposed. This is an R0 contract, not an implemented or approved remote surface. The 24 fixed names below cover P2 and the image requirement in T01; remote-enabled plugin names are additional and dynamic (`docs/plans/2026-10-27-aiboard-remote.md:223`, `docs/plans/2026-10-27-aiboard-remote.md:318`).

## Context

The cloud agent is the reasoning loop, D9 sets whole-machine reach with the current directory as default, and the Runner must reauthorize every operation (`docs/plans/2026-10-27-aiboard-remote.md:23`, `docs/plans/2026-10-27-aiboard-remote.md:40`, `docs/plans/2026-10-27-aiboard-remote.md:133`). The existing broker derives access from the tool, applies its approval policy, and issues a bound grant (`runner-v2/src/tool-broker.ts:274`, `runner-v2/src/tool-broker.ts:286`, `runner-v2/src/tool-broker.ts:411`).

The companion JSON lists 107 fixed definitions registered across Runner Build, Chat and toolbench contexts. It includes optional and hidden definitions; availability in one context does not imply availability in another. It excludes configuration-dependent extension/MCP names and exported but unwired factories. Runtime extensions register their own names (`runner-v2/src/extension-runtime.ts:78`); MCP names are generated from server and tool names (`runner-v2/src/mcp-tools.ts:156`, `runner-v2/src/mcp-tools.ts:266`). `createValidationEvidenceTools` is separate from the wired two-tool evidence factory (`runner-v2/src/evidence-tools.ts:50`), and the exported final-verification submission factory has no registration caller in `runner-v2/src` (`runner-v2/src/final-verification-submission.ts:217`).

Catalog conventions: `effect` and `readOnly` reproduce Runner declarations, whose effect enum is `none`, `workspace`, or `external`; `process` and `network` are not declared effect values (`runner-v2/src/agent-contracts.ts:159`). An effect of `none` does not establish that an operation changes no state: `extensions.plan_change` can apply a change when authorized (`runner-v2/src/extension-management-tools.ts:97`). Runner has no `permissionClass` field: that catalog field records `assessAccess().capability`, or the broker's effect fallback when no assessor exists (`runner-v2/src/agent-contracts.ts:257`, `runner-v2/src/tool-broker.ts:274`). `rolesAllowed` is the union in `role-capabilities.ts`, including optional entries; `unknown` means that file does not enumerate that definition, not that anyone may invoke it. The separate Architect lifecycle allowlist exists in `runner-v2/src/build-runtime.ts:5935`; subagent and toolbench registrations have separate contexts (`runner-v2/src/subagent-tools.ts:183`, `runner-v2/src/toolbench-session.ts:179`). A role allowlist is not itself an execution grant; some memory operations also enforce Architect identity at execution (`runner-v2/src/memory-tools.ts:159`, `runner-v2/src/memory-tools.ts:181`). `ownedOnly` marks operations targeting existing Runner-managed processes or browser sessions, not a claim that arbitrary artifacts or files are owner-scoped.

## Decision

Use unprefixed, lowercase snake_case names: the server already supplies the AIBoard identity, and short names are readable in both clients. Each fixed name is an MCP identifier. All fixed tools are subject to account, client, device, entitlement, Runner role, exact grant, audit, device policy and applicable approval checks; the denylist applies to Runner file tools. A model argument never supplies an approval, role, grant, actor identity, or authorized root. D17 requires no per-action approval by default; apply approval only when the device policy enables it, including under Full. Full currently bypasses the broker's ordinary approval test (`runner-v2/src/tool-broker.ts:286`, `docs/plans/2026-10-27-aiboard-remote.md:48`, `docs/plans/2026-10-27-aiboard-remote.md:187`). D15 puts these low-level tools first and defers Build-level tools to X3; D16 adopts the same surface for L1 local stdio MCP (`docs/plans/2026-10-27-aiboard-remote.md:46`, `docs/plans/2026-10-27-aiboard-remote.md:47`, `docs/plans/2026-10-27-aiboard-remote.md:163`, `docs/plans/2026-10-27-aiboard-remote.md:268`). (As built, 2026-11-12: L1 did not adopt this surface. The local door serves 20 tools, the 18 `LOCAL_TOOLS` plus `batch_files_read` and `batch_files_patch` in `runner-v2/src/remote-tool-runtime.ts`, with no job, device or artifact tools; the relay serves 26 tools, without `git_commit` or `browser`. See `docs/plans/2026-10-27-aiboard-remote.md` L1 and the tool-surface note under it.)

D17 supersedes the unchanged non-process catalog proposals where `expose_with_approval` implies mandatory default consent; for example, file mutations still carry that older proposal in the catalog (`docs/remote/r0/runner-tool-catalog.json:576`, `docs/remote/r0/runner-tool-catalog.json:615`, `docs/remote/r0/runner-tool-catalog.json:714`).

In the table, `D` means `deviceId?`; omission is valid only with exactly one authorized online device, otherwise return a typed selection error. `K` means a required caller-stable `idempotencyKey` for the logical effect. `repoPath?` selects a requested repository; Runner must validate it and derive the actual broker workspace, rather than accepting a model-authored execution context. Relative paths and `cwd` default to the device's launch directory under D9. `?` marks optional parameters. `R/D/I/O` are `readOnlyHint / destructiveHint / idempotentHint / openWorldHint`; `T` and `F` are literal booleans. `yes` means a new durable jobId is returned promptly; `maybe` means bounded inline completion or a jobId; `no` means no new jobId. A returned processId and jobId are distinct.

`files_search` is conservatively annotated non-read-only because its optional `cancel` ends a search session; ordinary queries are read-only. On local MCP, `process_read_output.view` is `output` by default or `snapshot` for `process.poll`; the remote path does not take it. Read-only hints do not replace authorization, and the idempotency key does not make a destructive tool generally idempotent.

`process_start` and both modes of `process_run` are available by default under D17 after S1's local device policy is implemented. Read-only or shell OFF blocks launch and stdin to existing processes; per-command approval gates launches and stdin when enabled. Read-only also blocks mutating tool actions. The file-tool denylist and `--only-here` do not confine commands or descendants by default; they may access files, credentials and networks available to the OS user. S2 is optional post-launch safe mode, not a launch prerequisite (`docs/plans/2026-10-27-aiboard-remote.md:186`, `docs/plans/2026-10-27-aiboard-remote.md:187`, `docs/plans/2026-10-27-aiboard-remote.md:266`). Today `process.run` grants a write path for `cwd` and invokes the selected executable/shell (`runner-v2/src/process-tools.ts:60`, `runner-v2/src/process-tools.ts:141`), while Full process-group execution is expressly unconfined (`runner-v2/src/execution-isolation-provider.ts:347`).

Managed process operations retain exact Runner ownership: `runId`, `sessionId`, actor role, and actor ID must match (`runner-v2/src/managed-process.ts:223`, `runner-v2/src/managed-process.ts:334`, `runner-v2/src/managed-process.ts:371`). R2 must durably bind a remote principal to that Runner-issued owner across reconnects without allowing callers to choose or widen it. The stdin channel is a pipe; `writeId` preserves the existing acknowledgement/uncertainty contract and EOF is distinct from a signal (`runner-v2/src/managed-process-tools.ts:61`, `runner-v2/src/managed-process-tools.ts:163`).

`git_commit` and `browser` were listed here until 2026-11-07, but no Runner ever mapped them (`REMOTE_TOOL_ID_TO_RUNNER` in `runner-v2/src/remote-connector.ts`), so every call failed with `unsupported_tool` and cost the model a turn. They are off the surface until a Runner can serve them. Commits run as git commands through `process_run`: `git.commit` keeps its task-branch check and worker role, and is not a general commit of an arbitrary current branch (`runner-v2/src/git-tools.ts:182`, `runner-v2/src/role-capabilities.ts:250`). A remote browser would also need the planned private-network and redirect protections, because the browser URL validator only checks HTTP(S) (`runner-v2/src/browser-tools.ts:604`, `docs/plans/2026-10-27-aiboard-remote.md:146`). `artifacts_read` and `image_inspect` with an artifact hash require a new account/device/job-to-artifact authorization proof: the current read tool verifies and fetches by hash without such a remote principal check (`runner-v2/src/artifact-tools.ts:56`, `runner-v2/src/image-tools.ts:37`).

## Results

These hold for remote and local MCP clients, which share one composition (`createGovernedBinding` in `runner-v2/src/remote-tool-runtime.ts`). Build's own agents keep their longer results.

- **One copy.** The relay returns a tool's result once, as content blocks, with no `structuredContent`. Clients that find `structuredContent` show it in place of `content`, so a copy there is what the model would read, and images would be lost. The base64 `inline` form stays only on a `jobs_result` page of a result too big for one page, which the 8 KiB block bound makes rare, and that page goes out once too, with the job's id for the next page.
- **Images.** `image_inspect` returns the image itself as MCP image content (base64 `data` and its `mimeType`), after a JSON block about the source and what was delivered. Over the remote path a PNG is downscaled until it is at most 180 000 bytes (`REMOTE_IMAGE_LIMITS` in `runner-v2/src/image-tools.ts`), so the whole result stays in the connector's 256 KiB inline result and comes back in one `jobs_result` page, the only form the relay decodes into content (`withImageContent` and `jobTool` in `runner-v2/src/remote-connector.ts`). The JSON says when the byte limit made the image smaller than `maxDimension`; a `crop` shows a region in more detail. A JPEG or WebP over the limit is refused, because only PNG is resized here. It is one image per call; local MCP keeps the provider limit (3.75 MB). The path rules are unchanged: the canonical path must be inside the workspace, so `..`, absolute paths and links that lead out are refused, and `artifactHash` stays refused.
- **Output in text blocks.** A read's output comes in text blocks, one per stream, after a JSON block about it, as `process_run`'s does. The broker bounds each block at 8 KiB and turns a larger one into a preview plus an artifact, so a page, at most 7 KiB of one stream, stays inline whatever it holds, and the model reads it without JSON escapes. A larger `maxBytes` still gets that page, and `hasMore` with the cursor brings the rest; a larger `tailBytes` gets the last page and says where it starts. Output that is not UTF-8 grows when decoded, each bad byte becoming three, so such a page is split over more blocks rather than cut.
- **Only what a model can use.** `process_run` returns `exitCode`, and otherwise only what differs from the normal case: a signal, an error, a timeout, unverified cleanup, lossy output, or confined execution. Reads drop identity, retention limits and offsets unless more output waits, and the cursor once nothing more can come. A start that waits reports the process's identity in a block of its own, because the connector binds the job to it, and then one read, instead of a snapshot plus a read of the same output. `process_signal` confirms the stop and leaves the output to `process_read_output`.
- **A summary starts where the output starts.** Above 6 KiB a stream comes back as its real head, its tail and the diagnostics between them, with 1-based line numbers, near 6 KiB. It is read from the stored output up to 16 MiB; past that, from the retained tail, and it says so. Its numbers are always the ones `search` and `lines` use; past a retention gap, where nobody can know them, lines carry no number.
- **A command's wait.** The relay waits for a `process_run` up to 45 s, or its `timeoutMs` if that is shorter, so most commands return their result in the one call. A longer one returns a `jobId` and keeps running until its `timeoutMs` (default 120 s, at most 30 minutes); the Runner's 120 s tool limit stretches to fit it, so its result still comes back, and `jobs_result` has it once the command has finished. A job in `process_start` is waited for by `process_read_output`, up to 30 s a call.
- **Nothing a finished command printed needs a second run.** When anything was left out, `process_run` returns `processId: "run-…"`, which `process_read_output` reads like a stopped process: pages, ranges, search, lines. The 32 newest are kept in memory for their exact owner. After a restart the id says the output is gone, and to run the command again. A `process_run` that times out or is cancelled gets the same result, local or remote: the text it printed and, when anything was left out, the id. Over the remote path its job still settles `outcome_unknown`, because nobody knows what the command did before it stopped, but the job now keeps that result instead of dropping it (`dispatch` in `runner-v2/src/remote-connector.ts`). The call's own wait and `jobs_result` return it as an error, after a line saying the effect is unknown and not to replay it blindly (`unknownOutcome` in `packages/relay/src/mcp-gateway.ts` in `aiboard-tunnel`). The result is evidence, not a resolution: the job stays `outcome_unknown` until a reconciliation, its key still returns the same job without running it again, and a cancellation's stop and effect stay unverified. Any other job whose effect is unknown keeps what its tool returned the same way. An older Runner stores nothing for such a job, and the relay then gives its old answer. A command that may outlast its limit still belongs in `process_start`.
- **Search.** `search` on `process_read_output` or `process_run` finds lines in everything kept: for a finished command up to 64 MiB of each stream plus its tail, for a live process its 128 KiB tail. A match has its 1-based `line`, its `byteOffset` (usable as `range.startOffset`) and optional context. It matches the text a terminal would show, one line at a time as in grep, while numbering the raw lines; a pattern that asks for a newline is refused, since it could never match. `exhaustive` means no match was missed. Bytes retention lost are listed in `notSearched`, `truncated` says why a search stopped early, and `splitLines` says a line over 1 MiB was searched in pieces, so a match across two pieces could be missed; such a line still counts as one match. The search is bounded: 10 s in all, 250 ms for one 1 MiB chunk, about 6 KiB of result. A regex passes the same safety screen as `until.pattern`.
- **Lines.** For these clients, `lines` on `process_read_output` reads by the same 1-based numbers across everything kept, not a window over one byte page; a negative `start` counts from the end of the output. A long result pages through `nextLine`. Where earlier bytes are gone, `linesRelativeToByteOffset` says what the numbers count from. On a running process the cursor such a read returns reads only what is printed after it, and `nextLine` reads the rest of what was there. Reading forward up to a retention gap ends with `gap`, and a negative `start` reads what comes after it; past one, `nextLine` is negative too, because a positive number would land before the gap.
- **Long-poll waits keep the lease.** A wait renews the owner's lease through its own end before it starts (`execution-host-managed-transport.ts`), so a read cannot wait past its lease and then fail on its own post-wait check. The fence check is unchanged: a stale owner is still refused.
- **Instructions.** Both servers publish how the tools fit together, for clients that put a server's instructions in the model's context. The relay sends `MCP_INSTRUCTIONS` (`packages/relay/src/mcp-tools.ts` in `aiboard-tunnel`) on `initialize` and `server/discover`. A local client gets `LOCAL_MCP_INSTRUCTIONS` (`runner-v2/src/local-stdio-mcp.ts`) on `initialize`: the relay's text without devices, jobs and the relay's 45 s wait. Its 120 s default and 30 s wait come from the Runner's constants. `runner-v2/test/local-stdio-mcp.test.ts` compares it with a copy of the relay's text, so a change to the local text or to those constants fails there until the copy matches it. The relay's text changes with the copy, and when the relay's text changes first, update the copy.
- **Errors.** Invalid arguments name the field (`files_write`: `content: required`) and never echo a value. The `submit_task` secret notice appears only to Build's own agents, because a remote or local client has no such tool.
- **Older Runners.** All of this needs the Runner release after 0.3.5, so release the Runner before deploying the relay. On an older Runner, `search` on `process_read_output` is refused with a clear message, `search` on `process_run` is ignored (or refused, when approvals are on), and `lines` counts from 0 within one page.

## Jobs

Jobs use record-before-dispatch admission in Runner, bind key + principal + payload digest, and reject conflicting reuse. An HTTP disconnect ends the wait only; cancellation returns `cancel_requested`, confirmed `stopped`, or `effect_outcome_unknown` distinctly. Never automatically replay ambiguous effects. When device policy enables approval, a `yes` response may initially be `awaiting_approval`; status/events/result do not create another job (`docs/plans/2026-10-27-aiboard-remote.md:142`, `docs/plans/2026-10-27-aiboard-remote.md:144`, `docs/plans/2026-10-27-aiboard-remote.md:193`). Each action and later result retrieval must recheck the appropriate current authorization.

For P2, only explicitly remote-enabled, individually allowed plugin tools may be listed. Publish each as `plugin_<normalized_server>_<normalized_tool>_<digest8>`; lowercase and replace other characters with underscores, bound the full name to 64 characters, and retain the digest suffix when truncating. Detect a collision and fail closed or expand the suffix. This denotes a naming rule, not an invented installed tool; bind the name to the exact Runner registration. Plugin calls also take `deviceId?` and, for effectful calls, `idempotencyKey`. Preserve Runner admission checks and apply conservative per-tool MCP hints. GUI plugins remain post-launch under D11, with separate opt-in and local safeguards (`docs/plans/2026-10-27-aiboard-remote.md:42`, `docs/plans/2026-10-27-aiboard-remote.md:259`). Existing MCP registration derives read-only status from both annotations, and current extension contracts provide `toolApproval` rather than a remote exposure switch (`runner-v2/src/mcp-tools.ts:164`, `runner-v2/src/extension-management-contracts.ts:78`). Never publish plugin capabilities that provide a parallel ungoverned filesystem, process or shell route.

## Consequences

The connector must route to the real broker and preserve effect, role, grant, ownership, revision, and extension checks; a remote action cannot become a Build Architect or verifier lifecycle call. A process may be visible in its original owner's process list after reconnect only if the durable binding restores that exact owner. Results may require chunking and artifact authorization before large output is usable (`runner-v2/src/managed-process.ts:223`, `runner-v2/src/artifact-tools.ts:62`, `docs/plans/2026-10-27-aiboard-remote.md:200`).
