# AIBoard Remote v1 contracts

**Status: proposed for R0 review.** These are protocol contracts, not a claim that the remote connector, job store, pairing endpoint, or relay integration is implemented. ADR-C is authoritative for job and cancellation shapes; ADR-A, ADR-F, and the remote tool surface supply the other proposed boundaries (`docs/remote/r0/adr/ADR-C-remote-jobs-idempotency-cancellation.md:50`, `docs/remote/r0/adr/ADR-A-connector-in-runner-lifecycle.md:33`, `docs/remote/r0/adr/ADR-F-browser-connect-handoff.md:13`, `docs/remote/r0/remote-tool-surface.md:19`).

| Schema | Root value and purpose |
| --- | --- |
| `remote-request.v1.schema.json` | Untrusted transport envelope, including the tool-specific `payload`. All identity, authorization, epoch, expiry and digest checks remain mandatory. |
| `remote-authorization.v1.schema.json` | Relay-signed per-request authorization carried beside the request as `{type:"request", request, authorization}`. The `signature` is base64url Ed25519 over the RFC 8785 canonical JSON of `claims`; the Runner verifies it under a pinned `relayKeys` entry, requires every claim to equal the request field, the audience to be the relay identity, and `scopeRef` to be locally authorized before epoch/expiry/nonce checks or admission. |
| `remote-response.v1.schema.json` | ADR-C response union: admitted responses require a job ID; non-admitted responses forbid one. An offline response requires `admission_unknown` or `not_dispatched`. |
| `job.v1.schema.json` | Runner-authoritative `RemoteJob`, its exact cancellation fields and states. `$defs/jobView` models the separately labeled offline projection; `$defs/cancelReceipt` models an offline pending cancellation. |
| `job-event.v1.schema.json` | Either one `RemoteJobEvent` or an ADR-C `RemoteEventPage` with opaque `nextCursor` and optional retention `gap`. |
| `connection-state.v1.schema.json` | ADR-A device connection states with proposed, state-specific reason codes and an authenticated epoch when connected. |
| `local-pair-exchange.v1.schema.json` | ADR-F request `{version, code}` or response `{version, instanceId, kind, port, sessionToken, peers}`. |
| `error.v1.schema.json` | Proposed typed error body and shared `errorCode` vocabulary used by the response. |

## Versioning and bounds

- Every `protocolVersion` is SemVer. These schemas accept major `1` only, including syntactically valid prerelease/build identifiers; a receiver must reject an unsupported major before admission. A prerelease is usable only when both peers explicitly support it.
- Minor releases are additive: new fields are optional, old meanings and required fields remain unchanged, and incompatible changes require a new major. Patch releases preserve the wire contract. Negotiate a mutually supported minor and validate against that minor's published schema. Closed objects reject unknown fields; an old validator must not silently ignore a newer field or assume that it understands an unnegotiated minor. `RemoteResponse`, `RemoteEventPage`, job views and cancel receipts use the already negotiated transport version, matching ADR-C; the local exchange instead has integer `version: 1`.
- IDs are nonempty strings up to 256 characters, opaque cursors/references/tickets up to 512, UTC RFC 3339 timestamps end in `Z`, SHA-256 digests are 64 lowercase hex characters, and positive sequences/epochs are decimal strings up to 19 digits. Compare decimal strings numerically, not lexically; fail closed rather than wrap or reuse on exhaustion.
- `payload` is deliberately open JSON because tool input shapes differ. Every nested string is at most 1,048,576 characters, array at most 1,024 elements, object at most 256 properties, and property name at most 256 characters. Event pages have at most 256 events; pair responses have at most three peers. Other objects are closed. These are proposed wire bounds, not a claim about current Runner limits. Byte-size and nesting-depth limits must also be enforced before parsing; their values require transport design and are not provided by these schemas.
- The connection reason vocabulary and pair `kind` values (`runner`, `accounts`, `legacy`, `bench`) are proposed v1 wire spellings for review, rather than existing Runner values. A state snapshot does not prove that a transition or tool is authorized.

## Validation beyond JSON Schema

A JSON Schema pass is necessary but never sufficient for admission, effect execution, or result access. The Runner must independently verify authenticated principals, audience/scope/entitlement, device ownership and epoch, timestamps, nonce, current grants, any approvals required by the current device policy, tool-specific input schema and canonical digest, and reauthorize before dispatch. D17 makes per-action approval opt-in by default (`docs/plans/2026-10-27-aiboard-remote.md:48`, `docs/remote/r0/remote-tool-surface.md:19`). A model-supplied `scopeRef` or payload is not authority. ADR-C defines the key as `(accountId, clientId, deviceId, idempotencyKey)` and the SHA-256 input as UTF-8 RFC 8785 canonical JSON of `{protocolVersion, deviceId, toolId, operationClass, scopeRef, payload}`; reject duplicate JSON keys and unsupported/non-finite values before hashing (`docs/remote/r0/adr/ADR-C-remote-jobs-idempotency-cancellation.md:17`).

The journal must atomically admit before dispatch, compare event sequences numerically and strictly increase them per job, bind cursors to the authorized job and principal, verify event/page job IDs, and report retention gaps. A schema cannot prove a valid state transition, a verified stop, result ownership or a side effect. `cancel_requested` is distinct from `stopped` and `effect_outcome_unknown`; a lost acknowledgment must not cause blind replay (`docs/remote/r0/adr/ADR-C-remote-jobs-idempotency-cancellation.md:18`, `docs/remote/r0/adr/ADR-C-remote-jobs-idempotency-cancellation.md:28`, `docs/remote/r0/adr/ADR-C-remote-jobs-idempotency-cancellation.md:36`).

ADR-C says a cancel of an already-settled job returns its proven state, but the closed `cancelReceipt` shape has no state field. A receipt and an authoritative job view must therefore be obtained separately; a receipt is the original idempotent acknowledgment, while the view carries the current state and cancellation evidence. This does not add fields to the v1 schema.

The local job store also needs distinct `storage_exhausted`, `not_found`, and `schema_migration_failed` errors, but the v1 `errorCode` enum does not include them. These are local errors; their wire representation requires a separately reviewed contract decision before job endpoints expose them.

The pair endpoint must validate exact Origin and Host, method, content type, instance and port, one-time ticket issuance, 256-bit entropy, expiry of at most 120 seconds and atomic consumption. The response's `sessionToken` is the fresh browser-session credential expressly allowed by ADR-F; it is not a valid pairing `code` and must never appear in a URL, argv or log. A peer response has no further peers, and its identity and port must match the launch. Static JSON Schema cannot establish any of these relationships (`docs/remote/r0/adr/ADR-F-browser-connect-handoff.md:13`, `docs/remote/r0/adr/ADR-F-browser-connect-handoff.md:19`, `docs/remote/r0/adr/ADR-F-browser-connect-handoff.md:23`).

The different-digest rejection code is `idempotency_conflict` (ADR-C spelling). The alternate `conflict_idempotency` from the T4 brief was removed by the architect before any release, so there is no alias; `error.invalid.retired-alias-conflict-idempotency.json` pins that.

## Fixture validation

A future focused test can use **Ajv 8** with its Draft 2020-12 entry point and **ajv-formats** for `date-time`. Register all eight schemas by `$id` before compiling references, enable format validation, then load each JSON fixture. The filename prefix maps to `<prefix>.v1.schema.json`, except `job-view` maps to `job.v1.schema.json#/$defs/jobView` and `cancel-receipt` to `job.v1.schema.json#/$defs/cancelReceipt`. All `valid/` files must pass their schema. All `invalid/` files must fail the complete protocol validation, with the following deliberately passing schema validation and failing the specified contextual check:

| Invalid fixture suffix | Fixed context and expected failure |
| --- | --- |
| `remote-request.invalid.expired-request.json` | Clock is `2026-10-27T12:00:00Z`; expiry is earlier. Reject `expired_request`. |
| `remote-request.invalid.device-epoch-mismatch.json` | Authenticated current/highest device epoch is `5`; the request carries `4`. Reject `device_epoch_mismatch`. |
| `remote-request.invalid.idempotency-key-conflict.json` | First admit `remote-request.valid.write.json` for the same principal/key. This request has a different correctly computed payload digest. Return `idempotency_conflict` without dispatch; `remote-response.valid.idempotency-conflict.json` is the corresponding response. |
| `job-event.invalid.nonmonotonic-page.json` | The page presents sequence `3` before `2`. Reject the out-of-order page even though each event has a valid shape. |
| `local-pair-exchange.invalid.reusable-token-as-code.json` | The supplied value is the `sessionToken` in `local-pair-exchange.valid.anchor-response.json`; the issued ticket is the distinct code in `local-pair-exchange.valid.request.json`. Reject it as an unissued ticket. |
| `local-pair-exchange.invalid.reused-pair-code.json` | The code was already consumed by a successful `local-pair-exchange.valid.request.json` exchange. Reject replay. |
| `remote-authorization.invalid.bad-signature.json` | Paired with `remote-request.valid.read.json` and the pinned test key below; the signature does not verify. Reject `unauthorized` with no admission or dispatch. |
| `remote-authorization.invalid.unknown-key.json` | Paired with `remote-request.valid.read.json`; `keyId` is not among the pinned `relayKeys`. Reject `unauthorized` with no admission or dispatch. |
| `remote-authorization.invalid.claim-mismatch.json` | Correctly signed over its own claims, paired with `remote-request.valid.read.json`; `claims.requestId` differs from the request. Reject `unauthorized` with no admission or dispatch. |
| `remote-authorization.invalid.scope-not-authorized.json` | Correctly signed over its own claims, paired with a request whose `scopeRef` is `scope-unapproved`; that scope is not in the session `authorizedScopes`. Reject `unauthorized` with no admission or dispatch. |

The valid authorization fixture `remote-authorization.valid.read.json` is signed for `remote-request.valid.read.json` under the synthetic test key `relay-test-1` whose SPKI public key (base64url, test-only) is `MCowBQYDK2VwAyEA-H9fcRUR-1SSE1fw-yuofxEwqpOFbkkl7QlyCibYLQA`. It proves the canonicalization and signature shape only; production relay keys are provisioned with the device session (P1) and never taken from the request.

For valid request fixtures use clock `2026-10-27T12:00:00Z`; the initial read and write use authenticated epoch `5`, and the retry uses epoch `6` after reconnect. Retry keeps the same principal, key, payload and digest while changing request ID, nonce, trace and epoch. The fixture data is synthetic. Also check the two valid request digests against RFC 8785 and SHA-256, and exercise duplicate-key parsing, cursor authorization, transitions, revocation, peer identity and stop evidence separately. The fixture shapes alone do not execute those checks.
