# ADR-D: Whole-machine remote scope

Revised 2026-10-27 for owner decisions D15–D17.

## Status

Proposed.

## Context

The owner chose whole-machine remote access with the starting directory as the default and an optional cwd-only mode (`docs/plans/2026-10-27-aiboard-remote.md:40`, `docs/plans/2026-10-27-aiboard-remote.md:48`, `docs/plans/2026-10-27-aiboard-remote.md:187`). Existing grants bind an actor, call, permission profile and canonical access paths/modes; `full` is one accepted permission profile. It is neither a wildcard path grant nor a sandbox (`runner-v2/src/execution-grants.ts:32`, `runner-v2/src/execution-grants.ts:51`, `runner-v2/src/execution-grants.ts:559`, `docs/runner-v2/security.md:12`).

`ToolBroker` normally derives paths from each tool and skips ordinary approvals for `full`; the filesystem mutation fence enforces the original exact grant and has specific alias restrictions. `fs.read` ultimately uses `readFile`, so a new remote deny policy must cover reads and traversal as well as mutations; existing checks alone are not the proposed whole-machine boundary (`runner-v2/src/tool-broker.ts:274`, `runner-v2/src/tool-broker.ts:286`, `runner-v2/src/tool-broker.ts:411`, `runner-v2/src/filesystem-mutation-fence.ts:184`, `runner-v2/src/filesystem-tools.ts:129`).

## Decision

### Scope and authority

Add a locally selected remote scope profile above the existing execution-grant system. Default Runner file-tool scope is every path the Runner's OS user can access, minus the non-overridable exclusions below; the invocation cwd is the default resolution/working directory, not a command security boundary. `aiboard remote --only-here` instead limits file tools to the canonical starting directory and descendants, still minus exclusions; it does not confine commands by default. Local owner selection and OS permissions remain necessary; relay scopes and model text cannot widen them. Permit a cwd that contains the configured state, including the home folder, with the state directory as an always-excluded file-tool subtree. Supporting this requires a reviewed replacement for the current state-outside-project guard with equivalent state protection; do not silently relocate state (`docs/plans/2026-10-27-aiboard-remote.md:59`, `docs/plans/2026-10-27-aiboard-remote.md:189`, `runner-v2/src/cli.ts:93`, `runner-v2/src/execution-host.ts:197`).

For every call, intersect the device policy, explicit remote tool/role policy, applicable approval and OS permissions. The broker still issues a short-lived, single-use grant for the **specific canonical paths and modes of the operation**; `full` does not create a blanket volume grant. An explicitly requested root listing may have a root read grant only with the independent per-descendant exclusion guard below. Set `externalApproved` only from locally enforced policy and any approval required by that policy, never from a request flag. No per-action approval is required by default; when per-command approval is enabled, enforce it even under `full`. A grant or model-generated approval text is not a human approval. Existing role surfaces remain unchanged; the new remote actor gets only its explicit surface (ADR-A).

The local per-device defaults are shell/process ON, approval OFF and audit ON. The owner may opt into per-command approval, read-only, `--only-here`, or shell OFF. Dashboard requests may narrow policy; only the local user may broaden it. Enabled approvals can be answered in the `aiboard remote` terminal or the account-authenticated dashboard, using a signed approval bound to the job. The first `aiboard remote` invocation displays a one-time notice that agents can run commands as the user and read what that user can, with restriction and disconnect/revoke instructions (`docs/plans/2026-10-27-aiboard-remote.md:187`, `docs/plans/2026-10-27-aiboard-remote.md:188`).

Apply the file-tool deny policy to the **actual target**, not only `assessAccess.paths`: for example `fs.stat` currently grants the parent to inspect a link (`runner-v2/src/filesystem-tools.ts:255`). Cover Runner file-tool reads, metadata, search, list, artifact/image reads, move sources and destinations, and recursive operations. Add a last-mile read/traversal guard tied to the original Runner grant; issuing a grant alone does not enforce a direct filesystem read. Ancestor listing/search must exclude denied descendants before opening or reading them, without exposing names or contents; moving/deleting a tree containing a denied object must be refused, not partially executed. Reject file operations whose complete traversal or target identity cannot be proven, including a target inside an excluded root. Audit refusals without secret contents.

### Always denied

The following are a minimum, not a claim to identify every credential. Resolve the *actual configured* Runner `--state-dir`, token/device-key locations, extension credential/secret directories, installer root/bin and relocated profiles from trusted local configuration on every startup. Deny the entire protected directory and descendants through Runner file tools, including aliases, for every accessible user home; if a required sensitive location cannot be determined or enforced, fail closed for the affected file capability. Environment overrides are taken from trusted local configuration, never remote arguments. The current CLI accepts a state directory and puts provider and extension credentials there; its extension home is separately configurable (`runner-v2/src/cli.ts:91`, `runner-v2/src/cli.ts:167`, `runner-v2/src/cli.ts:175`, `runner-v2/src/cli.ts:598`).

### Canonicalization and race handling

1. Resolve relative names against the canonical cwd; reject NUL, malformed/ambiguous names and traversal outside `--only-here`. Check the supplied name, each parent, the final canonical object and any destination against the exclusion set. Resolve allowed links only with bounded, handle-based verification; deny a symlink/junction/reparse point or mount alias when its target and identity cannot be proved. Missing targets require a verified existing parent and a no-follow create; recheck after creation.
2. Use stable filesystem/volume object identity, descriptor-relative/no-follow traversal and last-mile checks for reads as well as writes, not string prefix comparison or `realpath` alone. Check both names and object identities for denied roots and descendants. Refuse hard-linked files when confinement to the authorized object cannot be proved, and refuse unsupported filesystems, handles, alias types or races. Recursive enumeration must apply the policy per child. Existing mutation fencing performs repeated identity/revision checks but expressly is not an atomic kernel boundary against external writers (`runner-v2/src/filesystem-mutation-fence.ts:84`, `runner-v2/src/filesystem-mutation-fence.ts:129`, `docs/runner-v2/security.md:33`).
3. **Windows:** resolve long/8.3 spellings and junctions/reparse points to a verified final handle and volume/file identity; apply the actual volume's case behavior, including case-sensitive directories. Reject alternate data streams, device namespaces, named pipes, trailing-dot/space ambiguities and unprovable `\\?\`/`GLOBALROOT`/volume aliases. For UNC shares require an attested file-path provider that resolves server/share identity and enforces the same rules; otherwise return unsupported. Existing trusted mutation already refuses UNC, streams and ambiguous Win32 forms (`runner-v2/src/filesystem-mutation-fence.ts:119`).
4. **macOS:** use actual volume case and Unicode equivalence plus verified handle identity; resolve symlinks and mounted-volume aliases before policy checks. Reject paths whose APFS/HFS/network-volume identity or race-safe traversal cannot be established.
5. **Linux:** treat names as case-sensitive filesystem bytes; handle symlinks, bind mounts and mount namespaces by verified object/mount identity. Deny `/proc`, `/sys` and `/dev` pseudo-filesystem access remotely, including `/proc/*/fd`, `/proc/*/root`, `/dev/fd` and aliases; they can expose already-open handles or alternate roots. Require kernel-supported descriptor-relative resolution such as appropriately constrained `openat2`, or fail closed when equivalent evidence is unavailable. Apply equivalent denial to macOS/Windows handle and device namespace aliases.

The existing mutation fence rejects symlink/junction parents and checks exact original paths; preserve that stricter rule until a replacement has equal or stronger proof (`runner-v2/src/filesystem-mutation-fence.ts:88`, `runner-v2/src/filesystem-mutation-fence.ts:201`). A canonical spelling alone cannot detect a secret copied elsewhere, hard-link alias without reliable identity, or an independent privileged writer. No broad promise is made for filesystems or OS primitives that cannot meet these checks.

### Commands and plugins

The remote command surface is `process.run` in either argument-array or explicit shell mode, and `process.start` for managed background work. Both are available by default under the device policy; read-only or shell OFF blocks launch and stdin to existing processes, and per-command approval gates launches and stdin when enabled. Read-only also blocks mutating tool actions. These commands run as the OS user and can access files, credential services and network resources available to that user, including excluded files and paths outside `--only-here`. The Runner file-tool denylist and cwd checks do not confine commands or their descendants. The existing `process.run` assesses cwd and accepts commands or shell scripts, while `process.start` also assesses cwd; Full process execution is explicitly unconfined (`runner-v2/src/process-tools.ts:34`, `runner-v2/src/process-tools.ts:61`, `runner-v2/src/managed-process-tools.ts:23`, `runner-v2/src/execution-isolation-provider.ts:347`).

S2 is an optional post-launch OS sandbox safe mode intended to enforce the denylist and `--only-here` for commands and descendants. Choosing and qualifying providers, including their filesystem, credential-IPC and descendant guarantees, is S2 design work; it is not a prerequisite for the D17 default. Unsupported S2 platforms must say so and retain the D17 defaults (`docs/plans/2026-10-27-aiboard-remote.md:266`).

Owned `process.poll/list/read_output/signal/write_stdin` remain subject to exact remote actor/session ownership, fresh grants and current policy; stdin can cause effects and needs idempotency/uncertainty treatment, with approval when the enabled per-command policy applies (`runner-v2/src/managed-process.ts:135`, `runner-v2/src/managed-process.ts:334`, `runner-v2/src/execution-host-managed-transport.ts:153`). No global PID control. Plugin tools remain remote-disabled until individually enabled and filtered; do not expose an ungoverned alternative to Runner tools. A managed MCP wrapper alone does not constrain a plugin's filesystem or credential APIs, and the file-tool denylist is not a claim of plugin confinement (`runner-v2/src/extension-mcp.ts:614`, `runner-v2/src/extension-mcp.ts:633`).

## Consequences

This preserves whole-machine reach, while fail-closing unsupported file-tool path forms and filesystems. It requires new file read/traversal enforcement, trusted location discovery, local device policy and optional approval enforcement even under `full`. Default command access remains unconfined and must be disclosed. Lifecycle stop evidence does not prove all external effects were undone.

Focused per-OS qualification must cover allowed file-tool paths outside cwd and `--only-here`, every excluded category, aliases/links/hard links, case and Unicode behavior, concurrent path replacement, recursive listing/move/delete, home-folder startup and every device-policy option. Demonstrate the default command boundary honestly using benign fixtures; S2 separately qualifies any claimed command and descendant confinement. Unsupported file-tool enforcement must refuse before effect.

## Alternatives rejected

- A filesystem-root `full` grant: loses exact-call scope and includes excluded descendants.
- Claiming a cwd/path denylist confines unrestricted shells, interpreters or plugins: those processes can open paths and credential services independently.
- Requiring an attested command sandbox or per-action approval before default remote use: conflicts with D17; S2 and per-command approval are opt-in.

## Open questions

None for the default policy. S2 must choose and qualify any confinement providers for its optional safe mode.

## Plan corrections

The R0 packet asks which of `process.run`, `process.execute` and `process.shell` to expose, but only `process.run` is a registered tool; the other two are its assessed capability strings, as the updated evidence inventory now recognizes. `process.start` is a separate managed-process tool (`docs/plans/2026-10-27-aiboard-remote.md:71`, `docs/plans/2026-10-27-aiboard-remote.md:153`, `runner-v2/src/process-tools.ts:41`, `runner-v2/src/process-tools.ts:61`, `runner-v2/src/managed-process-tools.ts:23`). The plan's `full` grant wording must not be read as an existing whole-machine or exclusion-enforcing grant: `full` is an accepted permission profile and grants still require explicit access paths (`docs/plans/2026-10-27-aiboard-remote.md:154`, `runner-v2/src/execution-grants.ts:51`, `runner-v2/src/execution-grants.ts:559`). Existing strict selection attests exact-grant **write** confinement, not S2's proposed denied-read and credential-IPC boundary, and can select unconfined Full; the current OCI representation also rejects filesystem roots and parent-of-workspace grants (`runner-v2/src/execution-isolation-provider.ts:46`, `runner-v2/src/execution-isolation-provider.ts:347`, `runner-v2/src/execution-isolation-provider.ts:439`, `runner-v2/src/oci-execution-isolation-provider.ts:745`, `runner-v2/src/oci-execution-isolation-provider.ts:759`).

The plan allows cwd to contain state, but the current CLI and execution host reject that nesting. Supporting it requires a new, equivalently secure state/project separation, not just the new scope flag (`docs/plans/2026-10-27-aiboard-remote.md:59`, `docs/plans/2026-10-27-aiboard-remote.md:189`, `runner-v2/src/cli.ts:93`, `runner-v2/src/execution-host.ts:197`). The plan's unqualified per-action-consent wording and T08's unqualified unreachable-path wording must be read subject to D17: approvals are opt-in and the denylist applies to file tools, not default commands (`docs/plans/2026-10-27-aiboard-remote.md:48`, `docs/plans/2026-10-27-aiboard-remote.md:134`, `docs/plans/2026-10-27-aiboard-remote.md:186`, `docs/plans/2026-10-27-aiboard-remote.md:325`, `runner-v2/src/execution-isolation-provider.ts:347`).
