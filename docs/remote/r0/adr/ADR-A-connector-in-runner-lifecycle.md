# ADR-A: Connector in the Runner lifecycle

Revised 2026-10-27 for owner decisions D15–D17.

## Status

Proposed.

## Context

The CLI composes the execution host, supervisor, permission store, Build factory/manager and control server; it reconciles Builds before listening. The localhost server also exposes chat and tool-bench routes, so forwarding its HTTP surface would expose more than the intended remote tool surface (`runner-v2/src/cli.ts:115`, `runner-v2/src/cli.ts:225`, `runner-v2/src/cli.ts:290`, `runner-v2/src/cli.ts:303`, `runner-v2/src/control-server.ts:277`, `runner-v2/src/control-server.ts:374`).

The existing tunnel connector starts a separate stdio MCP child and forwards requests to it. Its socket has three transport states and its cancel frame only drops a pending response; neither establishes Runner authorization or effect cancellation (`D:/repos/aiboard-tunnel/packages/connector/src/connector.ts:82`, `D:/repos/aiboard-tunnel/packages/connector/src/connector.ts:148`, `D:/repos/aiboard-tunnel/packages/connector/src/connector.ts:207`, `D:/repos/aiboard-tunnel/packages/connector/src/tunnel.ts:38`).

## Decision

Compose a **remote service owned by the Runner V2 CLI**, alongside and dependent on the existing execution host, permissions, artifacts, extensions and their stores. It owns the outbound WSS connector, durable remote admission/journal, principal mapping, readiness and an explicitly registered remote tool surface. It has no child-process launcher. Expose **only Runner V2** through that service: never the account, legacy or benchmark runners, localhost control routes, provider credentials, or an AIBoard model loop. The relay routes but never issues local authority. The fixed owner decisions and trust planes are in `docs/plans/2026-10-27-aiboard-remote.md:32`, `docs/plans/2026-10-27-aiboard-remote.md:40`, `docs/plans/2026-10-27-aiboard-remote.md:133`.

| Stage | Required call or change |
| --- | --- |
| Verify | Authenticate each hop, device proof of possession and current epoch; verify signed account/client/device, audience, scope, expiry, nonce and entitlement against local policy. Reject untrusted model arguments as authority. Durably admit or find the job before dispatch (ADR-C). |
| Bind identity | Runner maps verified account + client + device to a locally generated, durable remote principal, run ID and logical agent-session ID. Keep that identity across reconnect for owned process follow-up; scope ownership and revoke it locally. Add a dedicated `remote` actor/role and explicit remote surface, updating all actor validators and persisted codecs. Never impersonate `worker`, `architect`, or `runner_internal`; never copy a Build's privileged lifecycle tools. Current actor types and grant validation do not accept `remote` (`runner-v2/src/agent-contracts.ts:4`, `runner-v2/src/execution-grants.ts:559`, `runner-v2/src/managed-process.ts:389`, `runner-v2/src/role-capabilities.ts:12`). |
| Compose | Use `ExecutionHost.bindRun(...)` with a Runner-created capability contract and current local profile; recover its binding, and use its `executionGrants`, `sessionAuthority`, `managedProcesses`, `commandExecution`, and streaming runtime. Construct `ToolBroker` with that same grant authority, `SqliteToolLedger`, artifacts and a policy-selected approval callback using `SqlitePermissionStore.requestTool` when required. Register the approved native definitions with `ToolBroker.register`; register explicitly remote-enabled extension tools with `registerExtensionTool`. Extend managed extension composition for a remote binding; current `ManagedMcpRuntime.buildTools`/`chatTools` are not a remote authorization API (`runner-v2/src/execution-host.ts:119`, `runner-v2/src/execution-host.ts:145`, `runner-v2/src/execution-host.ts:247`, `runner-v2/src/tool-broker.ts:69`, `runner-v2/src/tool-broker.ts:140`, `runner-v2/src/permission-store.ts:96`, `runner-v2/src/extension-mcp.ts:556`, `runner-v2/src/extension-mcp.ts:573`). |
| Authorize and invoke | Intersect the explicit remote allowlist, preserved role restrictions, current extension enablement/per-tool remote policy, operation class, local device policy and applicable approval. Bind each enabled human approval to the job, verified principal/device, tool, payload digest, canonical scope and expiry; revalidate it before effect. Dispatch a typed `ToolCallBlock` via `ToolBroker.invoke(call, context)` with Runner-derived run/session/actor/call ID and cancellation signal. Broker validation and access assessment precede its `executionGrants.issue`; only Runner puts the opaque grant in the execution context. Enforce the opt-in per-command approval gate even for `full`, because the current broker skips ordinary approvals under that profile; do not require per-action approval by default (`runner-v2/src/tool-broker.ts:206`, `runner-v2/src/tool-broker.ts:262`, `runner-v2/src/tool-broker.ts:286`, `runner-v2/src/tool-broker.ts:411`, `runner-v2/src/agent-contracts.ts:232`, `docs/plans/2026-10-27-aiboard-remote.md:48`). |
| Streaming operations | Do not call `SessionAuthority` as a login/session factory or mint a second grant. For `process.start`, register `createManagedProcessTools`; `ManagedProcessService.start` uses the `createExecutionHostManagedRuntime` registered for the binding, which calls `ExecutionHostRunBinding.openStreaming`. Runtime `open` invokes `SessionAuthority.stageLaunch`, `validateStagedLaunch` and `finalizeLaunch` with the broker grant and owned handshake. First operation uses `authorizeLaunchOperation`; later broker-issued grants go through `authorizeOperation` (or `authorizeObservationBatch`) and `assertOperationAuthorization`, preserving owner, fence and envelope checks. Filesystem and one-shot calls use their existing broker/grant paths, not a fictitious streaming session (`runner-v2/src/managed-process-tools.ts:18`, `runner-v2/src/managed-process.ts:81`, `runner-v2/src/execution-host.ts:759`, `runner-v2/src/execution-host-managed-transport.ts:103`, `runner-v2/src/streaming-process-session-runtime.ts:1440`, `runner-v2/src/streaming-process-session-runtime.ts:1535`, `runner-v2/src/session-authority.ts:520`, `runner-v2/src/session-authority.ts:540`). |

**Device policy:** the connector stores and enforces a locally authoritative per-device object, proposed as `{ processTools: true, approval: "none", readOnly: false, onlyHere: false, audit: true }`. The local user may opt into `approval: "per_command"`, read-only, `--only-here`, or process/shell OFF. Read-only blocks mutating tool actions; read-only and shell OFF block process launch and stdin to existing processes. Enabled per-command approval gates launches and stdin. The dashboard displays policy and may request narrowing; only the local user may broaden it. On the first `aiboard remote`, show a one-time notice that agents can run commands as the user and read what that user can, plus how to restrict access and disconnect or revoke. Runner file-tool exclusions do not confine default commands (`docs/plans/2026-10-27-aiboard-remote.md:48`, `docs/plans/2026-10-27-aiboard-remote.md:186`, `docs/plans/2026-10-27-aiboard-remote.md:187`, `docs/plans/2026-10-27-aiboard-remote.md:188`).

When approval is enabled, the user can answer in the `aiboard remote` terminal or the `mcp.aiboard.me` dashboard. Dashboard answers require account authentication and a signed approval bound to the job; the connector verifies the binding and current policy before effect. The terminal remains usable without a browser (`docs/plans/2026-10-27-aiboard-remote.md:60`, `docs/plans/2026-10-27-aiboard-remote.md:187`).

**Startup:** acquire the per-device owner lock; open/migrate the remote job store and epoch state; construct the graph; run `reconcileRunnerStartup`, Build and remote binding/process/effect reconciliation, permission and extension recovery; validate local policy and grants; then authenticate and synchronize the current device epoch. Only advertise tool-ready after all required evidence and dependencies are healthy. An authenticated socket may be connected-degraded during reconciliation or plugin failure. No new effects run while recovery is unverified. Existing extension open already invokes its own recovery; add remote recovery to the actual composition/coverage rather than treating a coverage declaration as proof (`runner-v2/src/extension-management-service.ts:210`, `runner-v2/src/runner-resource-cleanup.ts:78`, `docs/runner-v2/architecture.md:7`).

**State machine:** `disconnected -> authenticating -> connected-degraded -> tool-ready`; socket/auth loss returns to disconnected; loss of a required tool or reconciliation evidence demotes tool-ready to connected-degraded. Local pause, owner-lock loss, expired device policy/entitlement or unresolved recovery enters suspended and blocks new admission; recoverable suspension returns through authenticating and reconciliation. Device-key revocation from any state enters revoked, immediately blocks new calls and closes the socket; only local re-pair/reprovision creates a new identity and returns to disconnected. A single client's OAuth revocation blocks that client's calls and reconciles its jobs without revoking other clients or the device. Advertise per-tool availability: an optional failed plugin is absent and reported degraded, never falsely ready. In degraded state admit only individually healthy tools after their required recovery and security checks pass; unresolved owned-resource recovery blocks all new effects. State changes are durable/audited without secrets.

**Shutdown/restart:** stop admission and readiness first, close transport/timers, signal admitted jobs according to ADR-C, revoke grants, reconcile/stop owned children and plugins, then close bindings, stores and host in reverse ownership order. Extend `RunnerResources`/`closeRunnerResources` so failed cleanup stays a typed blocker and is retryable. On crash/restart reacquire lock, invalidate old in-memory grants, reconcile durable job and exact resource identities, advance/fence transport epoch, and refuse ambiguous replay; a network reconnect alone does not cancel owned work (`runner-v2/src/runner-resource-cleanup.ts:41`, `runner-v2/src/runner-resource-cleanup.ts:111`, `runner-v2/src/execution-grants.ts:259`).

## Consequences

Remote work inherits Runner lifecycle and ownership checks, but requires new principal/role, per-tool exposure, local device policy, optional remote approvals, job and epoch stores, and recovery wiring. Extensions remain subject to explicit remote enablement and filtering; a managed wrapper alone does not confine their host access (`runner-v2/src/extension-mcp.ts:614`, `runner-v2/src/extension-mcp.ts:633`). A lost socket is not a job cancellation.

Focused qualification must exercise fake-relay read and owned-process calls, principal/scope forgery, stale epochs, restart before readiness, plugin loss and Ctrl+C cleanup on each supported OS. No socket state or passing mock alone establishes production readiness.

## Alternatives rejected

- Forwarding `ControlServer` or a standalone stdio MCP child: exposes unrelated APIs or bypasses the Runner-owned grant graph.
- Reusing a Build actor or `runner_internal`: conflates principals and can inherit unrelated authority.
- Treating WebSocket heartbeat as readiness: does not establish recovery or tool availability.

## Open questions

None: the terminal and authenticated dashboard are the selected approval channels.

## Plan corrections

The plan lists `runtime-router.ts` with identity/fencing; its `RuntimeRouter` selects model workers/verifiers and handles provider routing, not remote principal or device fencing. Remote mode should not invoke it (`docs/plans/2026-10-27-aiboard-remote.md:79`, `runner-v2/src/runtime-router.ts:105`, `runner-v2/src/runtime-router.ts:135`, `runner-v2/src/runtime-router.ts:207`). The existing `SessionAuthority` governs streaming-session launches/operations, not general remote login (`runner-v2/src/session-authority.ts:214`). The plan's unqualified high-risk per-action consent in §3 is overridden by D17's opt-in approval policy (`docs/plans/2026-10-27-aiboard-remote.md:48`, `docs/plans/2026-10-27-aiboard-remote.md:134`).
