# Q1 — Security qualification: threat matrix (draft, updated 2026-11-05)

**Status values:**
- **Covered:** controls exist and executed tests prove them (red/green where noted in the ledger).
- **Partial:** controls exist, but evidence is missing for some OS, case or layer.
- **Gap:** no adequate control yet.
- **Blocked:** depends on a packet not started (X1 plugins).
- **Accepted:** residual risk the owner has explicitly decided to carry.

**Sign-off: not signed.** Q1's DoD needs an independent reviewer to re-run the cited suites and sign this matrix. That's a Stage 2 gate; Stage 1 only needs Q1 in progress. Every status below is the author's own reading until then. Ledger references point to `docs/plans/2026-10-27-aiboard-remote-STATUS.md`.

| # | Threat | Controls | Evidence | Status |
| --- | --- | --- | --- | --- |
| 1 | **Cross-tenant leak**: reading or calling another account's device, job, app or usage | Every lookup is scoped by `accountId` (repository, gateway, device route, dashboard API). Foreign ids get the same reply as unknown ids. The Runner re-checks account, client and device on every request. | relay `accounts-devices`, `mcp-gateway` (foreign device, name-as-id), `pairing-v2`, `device-route` (cross-account send never reaches the Runner); P1a mutants (account scoping ×2, repository-level); cross-repo interop P1b 6/6, R4 7/7; runner `remote-actor-binding`, `remote-admission` | Covered |
| 2 | **Stolen or expired MCP token** | Opaque access tokens with a 1 h TTL. Refresh rotation, and reuse of a rotated refresh token kills the grant. Revoking the grant kills its tokens, and so does a disabled account. The gateway re-verifies the token on every request (stateless). | `oauth-flow` (refresh reuse, deleted grant, disabled account, code replay revokes tokens); live lockout test 1 on staging (Claude refresh → `invalid_grant`) | Covered |
| 3 | **OAuth audience confusion** | Single resource `${origin}/mcp`. The verifier checks `aud` and the grant's resource. Tokens for a foreign resource are refused at the authorization step. | `oauth-flow` (foreign resource refused; stored token rewritten to a foreign, multi-valued or missing `aud` is refused with the grant intact, red with the check off — aiboard-tunnel `remote/p4a-dashboard`) | Covered |
| 4 | **DCR / CIMD abuse**: client flooding, SSRF through client metadata, impersonating a known client | CIMD only from allow-listed hosts (three layers), with a DNS-pinned https fetch (5 s / 64 KiB). DCR is limited to public clients with https or loopback redirects, 10 per IP per hour. Redirect URIs must match exactly. The consent screen shows the client host. | `oauth-flow` (off-allow-list CIMD never fetched, DCR profile and rate limit, redirect mismatch); `oauth-policy` | Covered |
| 5 | **Path traversal through Runner file tools** (symlink, junction, `..`, UNC, case, 8.3, ADS) | `remote-path-guard` canonicalizes paths, and the always-denied set covers AIBoard state, credential stores, `~/.ssh`, browser profiles and cloud CLI credentials. | runner `remote-path-guard` 10/10 including a real 8.3 alias (Windows); `remote-home-start` | Partial: the macOS and Linux matrix is CI-only and still pending |
| 6 | **Shell commands bypassing the denylist** | By design (D17), shell and process tools run as the OS user. The one-time notice says so. Opt-in controls: shell off, read-only, only-here, approvals. | runner `remote-device-policy`, `remote-approvals`; the dashboard now shows each device's policy | Accepted by the owner 2026-11-05 (D17); S2 sandbox comes post-launch |
| 7 | **Malicious plugin descriptors**: tool-name spoofing, oversized schemas, a plugin claiming built-in tools | Plugin tools are namespaced `plugin_<server>_<tool>_<digest8>` and only admitted through Extension Management with a trust policy. | runner `remote-extension-policy` | Partial: the remote-exposure switch and catalog arrive with X1 (Blocked) |
| 8 | **Prompt injection via files, tools or web**, steering the cloud agent | AIBoard cannot stop a cloud model from being steered by content it reads. What it does guarantee: tool permissions never come from model text, and a policy can only be narrowed remotely, never broadened. Audit is on by default. | runner `remote-device-policy` (only the local user can broaden). Stated in the Terms ("Your computer, your responsibility"), and in the privacy page and first-run notice from the approvals change (behzad62/aiboard, branch `claude/dashboard-approvals`). With shell on, a misled model can run anything the account can: those texts say so | Accepted by the owner 2026-11-05 (inherent). The notice reaches users with Runner 0.3.5 |
| 9 | **Model-generated "approve" text** | Approvals are off by default and cover process tools only, not file tools. They are answered in the local terminal or on the signed-in dashboard page, never through an MCP tool, so text in a tool result can't answer them. Each is bound to a per-job, single-use nonce the dashboard never sees. A dashboard answer is signed by the relay for that account, device, connection epoch, job and nonce, lives 60 s, and is verified by the Runner; the first answer wins. **Residual:** the relay can sign answers, so a compromised relay can approve commands (row 11). Anything able to drive the person's signed-in browser could also click Allow. | runner `remote-approvals` 17 tests, 21 refused-answer cases; relay `device-route`, `accounts-devices`, `mcp-gateway`, `dashboard`; real browser `relay.spec.ts` (hostile text, CSP, phone width); real connector against real relay (other account refused, runs once, denial blocks, late answer does nothing); 32 mutants all red. No real AI client yet | Covered on the branch, pending staging with a real client |
| 10 | **Webhook forgery and fake payment redirect** | Paddle signature verification over the exact body, price-ID allow-list, idempotent processing; the redirect grants nothing. Billing stays off unless `PADDLE_*` is set. | billing `signature`, `store` (replayed and out-of-order series, prices outside the allow-list); relay `billing-http`; Paddle sandbox end-to-end on staging 2026-11-02 | Covered for the sandbox; repeat with live Paddle before charging anyone |
| 11 | **Relay compromise blast radius** | The relay is not an execution authority, but it signs per-request authorizations and holds the root key that signs pairing sessions. A compromised relay can therefore drive every connected device of every account, within each device's local policy. Devices keep data local; audit is local; local revoke and Ctrl+C always work. | design (§3); `device-route` forged-signature tests show that only relay keys are trusted | Accepted by the owner 2026-11-05 **for the beta only; reopen before paid launch.** Dashboard approvals widen this slightly: a compromised relay can also approve commands on devices that require approval (row 9). Mitigations to consider: an offline root key (sign the relay key set offline), per-account tool-call alerting, a terminal-only approvals option, and making the S2 sandbox the default later |
| 12 | **Relay signing-key leak** | R4e rotation: a root-signed key set in every challenge, with monotonic `issuedAt` on the Runner. | runner `remote-connector` rotation suite (every refusal case, replay, downgrade); cross-repo interop 5/5 (rotate A→B without re-pairing, downgrade refused); mutants red (no downgrade guard, no monotonic check) | Covered |
| 13 | **Root key leak** | Pins are compiled into the Runner. Recovery is a Runner release pinning only a new key, then the relay moves to it. Devices keep their pairing. **Residual:** nothing can remove trust from a Runner that hasn't updated, so users must be told. Runbook: `docs/remote/root-key-rotation.md`. | Drill 2026-11-05 on this PC: real connector and transport against the real device route, planned rotation and leak, 11 checks as expected. Not run on staging or through a real release | Partial: run it once on staging |
| 14 | **Token or secret leakage** in logs, URLs, Referer or argv | Structured redacted logs; `no-referrer` on `/auth` and `/api`; pairing uses a fragment code with ≤120 s TTL; no tokens in URLs; `__Host-` cookies (HttpOnly session, Secure, SameSite=Lax). | relay `accounts-logs`, `device-route-ops` (T18 log-leak check, red/green), `oauth-flow` (no secrets in logs), `pairing-v2`; runner `remote-pairing` | Covered |
| 15 | **CSRF, Origin and clickjacking** on browser routes | Double-submit CSRF token bound to the session, plus an exact Origin check on every non-GET. `frame-ancestors 'none'` and `X-Frame-Options: DENY` on every HTML page. | P1a mutants (CSRF, Origin); `oauth-flow` (consent CSRF/Origin); `dashboard` (headers) | Covered |
| 16 | **Dashboard XSS** | CSP `script-src 'self'` with no inline script or style; every API string goes through `textContent`. A static check rejects `innerHTML`, `insertAdjacentHTML`, `eval` and `new Function`. | relay `dashboard` 7/7, including hostile names rendered as text | Covered |
| 17 | **Device impersonation or replay** | Ed25519 device key in the OS secret store; relay-signed challenge; single-use proof; epoch fencing; a revoked device is told only after its proof verifies. | relay `device-route` (impostor gets `auth_error`, real key gets `revoked`/4003, status frame never counts as a proof); runner `remote-connector` (forged challenge persists nothing) | Covered |
| 18 | **Pairing-code phishing**: user approves an attacker's device | Short code with a TTL, a `sameNetwork` hint, and the device name and platform on the approve page. Approval needs a signed-in, CSRF-checked session. | P1b mutants (`sameNetwork` forced, approval bound to another account) | Partial: device-code phishing is inherent. Consider showing the approving IP or country beside the device's, and a warning when they differ |
| 19 | **Resource exhaustion** | Caps on unauthenticated upgrades per device and globally, pending requests per device and account, transfers per connection, request bodies and frame sizes; credit window on artifacts; per-IP DCR limit. | relay `device-route`, `artifact-pipe` (bounded relay memory), `server`; runner `remote-artifact-transfer` | Partial: P3a metering enforces monthly plan limits, but nothing limits the rate of tool calls for an account. The beta is open to any Google or GitHub account (owner 2026-11-05). Idle capacity measured 2026-11-05: the real image under its 320 MB limit held 12,000 authenticated idle devices, peaking at 200 MiB, with none lost. That ran on a developer PC without nginx, TLS or tool calls. The likelier limit is nginx on the VPS: `deploy/` doesn't set `worker_connections`, and the VPS has 768 (read 2026-11-06). Behind its SNI stream router a device should use 4 nginx connections (client, router to loopback, the loopback accept, relay), shared with the other sites on that nginx. That is about 190 devices per worker, from the config rather than a measurement; the worker count and open-file limit aren't read yet. Q2 still has to measure active load |
| 20 | **Backup or restore reviving revoked state** | Restore marks devices revoked unless they are explicitly kept, and audits the restore. | storage `storage` (R4c) | Covered |
| 21 | **Supply chain and licenses** | Pinned dependencies and a digest-pinned image; release signing (D18, L2). | `docs/remote/q1-license-inventory.md` (2026-11-05): nothing blocks distribution; `@github/copilot` carries redistribution conditions, which the build appears to meet. Checked from lockfiles and build code, not a released bundle; base image OS packages not inventoried | Covered for the beta; repeat before Stage 2 |
| 22 | **Privacy and retention** | The relay stores identities, devices, grants, usage counters and redacted logs only. Tool-call content isn't stored; a command waiting for a dashboard answer stays in memory only. Account deletion and 30-day log retention are in place. | Published at aiboard.me/privacy and /terms; `accounts-logs`, `device-route-ops` (log-leak checks); a mutant proves the approvals test fails if a command reaches the log | Covered. The approvals wording ships with that change |
