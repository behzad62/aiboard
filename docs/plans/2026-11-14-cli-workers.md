## 0. TL;DR

- **What.** The owner's Codex CLI, Claude Code and agy run as Build workers next to API-model workers. The Architect, its prompts and its tools do not change (OD-33).
- **Why it is a small change.** The scheduler talks to a worker through one call, `WorkerRuntimeDriver.run(assignment) → WorkerOutcome` (task-scheduler.ts:103-111). `NativeWorkerDriver.run` picks the runtime, creates the task's worktree and builds the context, then calls `runWorkerTask` (native-worker-driver.ts:324-646, inside `run` at :213-262). A CLI worker replaces only that call. Everything after a submission (review, verification, integration) already works on the worktree's git diff, whoever produced it.
- **How a CLI worker runs.** The Runner starts the CLI headless (`codex exec`, `claude -p`, `agy -p`) as a managed process it owns, in the task's worktree, with the task prompt on stdin and a JSON result schema. When the CLI delivers its result (Claude Code's and agy's `result` event, which ends the turn even while a background task keeps the process up) or exits (Codex), the Runner proves every process it started is stopped, undoes the CLI's own commits, re-runs the checks the CLI reports as evidence, and submits through the same code path as `submit_task`.
- **What the Runner trusts.** Only what it ran itself: the worktree's diff, its re-runs of the reported checks (with their output files, VF6), and its own final check. The CLI's report is a claim, shown to the Architect as one.
- **Failures.** Each CLI's quota, login, rate-limit and crash messages map to the provider-health kinds the Runner already uses. The existing failover hands the same task, in the same worktree, to another healthy worker, API or CLI, with a handoff summary in both directions (native-worker-driver.ts:586-616).
- **Settings.** CLI worker settings live in the AIBoard home (§6.5 of the 2026-11-03 plan). Settings shows the free checks (installed, logged in, models) and a Test button that sends one tiny prompt. The CLI's login stays in the CLI's own files; AIBoard never reads them.
- **Safety.** Full access only (OD-36). The CLI runs under the Runner's process ownership, and nothing in it is weakened: an unverified stop never submits, and it pauses the run with the worktree claim kept. A launch, stop or browser start the Runner cannot prove is the Runner's failure, never the CLI's (§3.11). The CLI browses with the Playwright CLI session the Runner starts for it (VF7b).
- **Where it runs (CW0, CWD-10, CWD-11).** v1 is a Windows feature. On Linux, Codex and Claude Code run every shell command in a new session, outside the process group the Runner can prove stopped, so CLI workers are refused on Linux and macOS (§3.11). On Windows, Codex left processes outside the Runner's Job in 3 of 7 CW0 runs, so Codex workers are refused on Windows too until CW0b explains the escape and a fix lands; Claude Code and agy run on Windows.
- **Estimate:** 17.5–24 days in thirteen packets (§5). The 2026-11-11 design estimated 13.5–17.5 days plus 1–2 for browser replay; §5.1 reconciles the two.

## 1. Goals and non-goals

### 1.1 Goals
1. A Build crew can include Codex CLI, Claude Code and agy workers next to API-model workers, chosen in the same crew picker.
2. The Architect is unchanged. It plans, reviews and decides exactly as today, and sees a CLI worker's submission in the same shape as any worker's.
3. A CLI worker's work meets the same evidence rule as any worker's: a criterion is supported only by evidence the Runner recorded for the assigned worker (acceptance-contracts.ts:302-306).
4. The owner can check each CLI before a Build: installed, logged in, models, and a Test button that shows why a CLI cannot work (not installed, not logged in, out of usage, model unavailable, timed out).
5. A CLI that runs out of usage or is logged out mid-Build hands its task to another worker automatically, as an API worker does today. A passing Settings test ends its cooldown.
6. Settings for CLI workers are home settings, saved through the Runner as op batches like every other setting.
7. Process ownership stays fail-closed: every process a CLI starts is owned, stopped and proven stopped like any managed process. Where CW0 showed that a CLI's processes leave the containment (Codex and Claude Code on Linux, Codex on Windows), or where it was not measured (macOS, agy on POSIX), that CLI is refused on that OS (§3.11).
8. PR CI stays at about 3 minutes per job: CLI tests use fake CLIs, never a real one.

### 1.2 Non-goals
- A CLI as Architect, reviewer, plan critic or verifier. A CLI cannot run AIBoard's own tool loop.
- Simple Build tasks or `aiboard exec` run by a CLI. That is NX7 of the 2026-11-03 plan; admission refuses a CLI runtime with `runtime_unsupported` until then (2026-11-03 plan §9).
- AIBoard's tools exposed to a CLI over MCP. Rejected in the design session: the CLIs' MCP time limits (Codex 60 s per call, Claude Code moves calls over 120 s to the background where `-p` loses them) break long test runs, and it would open a new way into the Runner.
- Answering a CLI's own permission prompts, or any access level below Full (OD-36).
- Questions to the Architect in the middle of a CLI's run. A CLI asks only at the end, through its result.
- Reading, storing or forwarding a CLI's credentials, or running a CLI in API-key mode from the home. The CLI uses the user's own login (OD-35).
- Other CLIs (opencode, gemini-cli, aider). The adapter interface allows them later.
- The legacy browser Build engine and the benchmark tracks.

## 3. Design

### 3.1 Names and the runtime config
- Call them **CLI workers**, with a `cli` transport (2026-11-03 plan §6.5). "Delegate" means `aiboard exec`.
- Provider ids: `codex-cli`, `claude-code`, `agy`. Health is per provider id (§2.3), so one Codex login out of usage cools every Codex worker, which matches how CLI quotas work.
- Runtime ids: `<providerId>:<model or "default">`, for example `claude-code:default`, `codex-cli:gpt-6-codex`. A crew may hold several workers of one CLI, each in its own worktree.
- `RunnerProviderConfig` gains `transport: "cli"` and an optional `cli: { reasoningEffort?: string }` block. A `cli` config:
  - has no secret, no base URL, no `runnerToken` and no `secretSource`; `validateProviderConfigs` accepts an empty `secret` for it and refuses any of the others;
  - passes through HM3 as pushed (`takesKeyFromHome` is false for it), and is never sent through the model proxy;
  - has `billingBasis: "account_not_metered"`, and `supportsTools: false`.
- The model id and effort are checked against a small character set (`[A-Za-z0-9._:/-]`, at most 128 characters), because they become arguments.
- CLI providers are not in `MODEL_CATALOG` or the provider registry: they are worker-only, never chat models. The Runner's catalog snapshot (OD-30) is unchanged; Claude Code's model list only reads its Anthropic entries (§3.2).

### 3.2 Detection and the free checks
Free checks cost no quota. Run on this PC on 2026-11-14 (version and login commands only, no prompt):

| | Codex CLI | Claude Code | agy |
|---|---|---|---|
| Installed here | `codex.exe` 0.167.1 | `claude.exe` 2.1.325 | `agy.exe` 1.5.6 |
| Version | `codex --version` | `claude --version` | `agy --version` |
| Logged in | `codex login status`: exit 0, "Logged in using ChatGPT" | `claude auth status`: exit 0, JSON with `loggedIn`, `authMethod`, `subscriptionType`, `loginExpiresAt` (also account fields, which AIBoard never stores or shows) | no status command; `agy models` exits 0 only when logged in |
| Models | `codex debug models`: Codex's own model catalog as JSON, no prompt (10 here: `slug`, `display_name`, `visibility`, `supported_reasoning_levels`, `default_reasoning_level`) | no list command; AIBoard's catalog Anthropic models, as the Anthropic provider lists them | `agy models`: one id and name per line (18 here) |
| Headless | `codex exec` | `claude -p` | `agy -p` |

- **Lookup.** The executable is resolved once on PATH with the same lookup VF2 uses for checks (check-tool-lookup.ts), and the resolved path is recorded. An `executablePath` in the home overrides it.
- **Windows launch form.** All three are `.exe` files here. An npm-installed CLI is a `.cmd` shim, which runs through `cmd.exe`. The Runner never puts model text in argv (the prompt goes on stdin, §3.5), and the remaining arguments are Runner-built and charset-checked, so a `.cmd` shim is safe to launch when none of its arguments has a character both Windows launchers refuse in a `.cmd` argument (`" % ! ^ & | < > ( )` or a line break; §3.5's open point). Claude Code's inline schema always has quotes, so only its `.exe` is launched; a Codex or agy `.cmd` is launched only when its state and worktree paths are free of those characters. A path that is neither `.exe` nor `.cmd` is refused on Windows.
- **Hosts that refuse `.cmd` launches.** When the batch-argv probe is not `verified` (as on GitHub's Windows image), the Runner refuses every `.cmd` and `.bat` launch with `WindowsBatchLaunchUnavailableError` (windows-process-backend.ts:32-38, :372-383). The free checks read the same fact the Job backend gets (`windowsBatchArgv`, native-build-factory.ts:1142): a CLI whose resolved executable is a `.cmd` on such a host is reported as "this PC can't launch .cmd CLIs", in Settings (CW3) and before planning (CW4), and is unhealthy before any task is assigned. So it never reaches a launch. If one does (the fact changed, or a resume), how it is handled depends on CW5a. After CW5a, the refusal arrives as `WindowsBatchLaunchUnavailableError` with its code, `windows_batch_argv_unverified`, and the managed record is stopped, so it is case 1 of §3.11. Until CW5a lands, it arrives as the unverified-cleanup aggregate of §2.7 and is handled as case 2: the run pauses and keeps the claim. That is fail-closed. An unverified cleanup is never read as proof that nothing started.
- **Model lists (CWD-9).** Each adapter lists its CLI's models the way Settings browses the OpenAI and Anthropic providers, behind one adapter call, `listModels() → { id, name, reasoningEfforts?, source }[]`, so the crew picker and Settings treat every CLI alike:
  - Codex CLI: `codex debug models`, keeping only `visibility: "list"` entries, with `supported_reasoning_levels` as the effort choices. It is a debug command whose shape may change: output that does not parse falls back to the catalog's OpenAI models, marked `source: "catalog"`.
  - Claude Code: the Anthropic entries of the Runner's catalog snapshot (runner-v2/src/generated/model-catalog.ts, OD-30), the same models the Anthropic provider lists (lib/providers/anthropic.ts:790-794), plus Claude Code's own aliases (`opus`, `sonnet`, `haiku`) that `--model` accepts.
  - agy: `agy models`.
  - Every list also offers "CLI default" (no model flag). A listed model is a suggestion, not a promise that the user's subscription includes it: the Test button confirms it, and a model the CLI rejects in a Build is `authentication` (§3.8). A typed id stays possible for a model no list shows yet.
- **Where they run.**
  - When Settings opens, and on its Refresh button, through `GET /v2/cli-workers` (CW3). Results are cached for 60 s.
  - Before planning, for every CLI in the crew, recorded with the tool inventory (VF1) as one `cli_workers.checked` event. A CLI that fails a free check is recorded as unhealthy with the matching failure kind (§3.8) before any task is assigned, so a logged-out CLI is caught before work begins.
- **Bounds.** 8 s per probe (the inventory's timeout, verification-inventory.ts:32), no network beyond what the CLI itself does for `agy models` and `codex debug models`, no file written. Output is cut to the first lines the parser needs. The parsers keep only the fields named above.

### 3.5 The worker loop
For a runtime whose config has `transport: "cli"`, `NativeWorkerDriver.run` takes a CLI branch in place of `runWorkerTask` (native-worker-driver.ts:440). Everything before it (selection, contract check, worktree, context pack, context manifest) is unchanged. The branch lives in a new `cli-worker-runtime.ts`; the per-CLI details live in `cli-worker-adapters.ts`.

1. **Prompt.** The same context pack text an API worker gets (native-worker-driver.ts:397-438), then a preamble that restates the worker rules for a CLI:
   - work only in this folder (the worktree); do not commit, push, install packages globally, or change Git config;
   - `docs/project/**` is the Architect's;
   - verify by impact, narrowest first; never weaken a test; run each check as its own command;
   - for UI work, use the running Playwright CLI session (§3.10);
   - end with the JSON result below, and list every check you ran.

   A handoff section follows when another worker worked on this attempt before (§3.9). On a fix round, the prompt is the re-run results instead (§3.6).

   ~~~ts
   interface CliWorkerResultV1 {
     outcome: "done" | "needs_decision" | "cannot_do";
     summary: string;                        // at most 4,000 characters
     question?: string;                      // needs_decision
     replanReason?: string;                  // cannot_do
     checks: { label: string; executable: string; args: string[]; cwd?: string;
               outputs?: string[]; criterionIds?: string[] }[];   // at most 12
     notRun?: { what: string; why: string }[];
     concerns?: string[];
   }
   ~~~

   The schema file the CLI gets is this interface in OpenAI's strict-mode form, which Codex's `--output-schema` requires: every field required, `additionalProperties: false`, and the optional fields (`question`, `replanReason`, and a check's `cwd`, `outputs` and `criterionIds`) required but nullable; `notRun` and `concerns` required arrays, empty when unused. The parser maps `null` to absent. CW0 ran a reduced form of it (runner-v2/test/fixtures/cli-workers/result.schema.json, without the three check fields).

2. **Launch.** Through `ManagedProcessService.start` with the worker's owner (run id, session id, worker actor), `interactive: true`, cwd = the worktree. The prompt is written to stdin and stdin is closed (`closeInput`). The result schema and the CLI's output file go to a Runner-owned folder outside the worktree (`state/cli-workers/<runSegment>/<sessionSegment>/`).

   | | Arguments (all Runner-built) | Prompt | Result | Resume |
   |---|---|---|---|---|
   | Codex CLI | `exec --json --output-schema <file> -o <file> [-m <model>] [-c model_reasoning_effort=<e>] --dangerously-bypass-approvals-and-sandbox -C <worktree> -` | stdin (`-`) | `-o` file; usage and the thread id from `--json` events | `exec resume <threadId> -` |
   | Claude Code | `-p --output-format stream-json --verbose --json-schema <schema> [--model <m>] [--effort <e>] --dangerously-skip-permissions --session-id <uuid>` | stdin | the `result` event on stdout (`structured_output`, `usage`, `is_error`); it ends the turn | `-p --resume <uuid>` |
   | agy | `--input-format stream-json --output-format stream-json --json-schema <file> [--model <m>] [--effort <e>] --dangerously-skip-permissions --print-timeout 0 -p=` | one line on stdin: `{"event":"user","message":{"content":"<prompt>"}}`, then EOF | the `result` event on stdout | `--conversation <id>` |

   Amended after CW0 (docs/runner-v2/cli-workers-spike-2026-11-17.md §2), which confirmed every Codex flag:
   - **agy.** `-p` is a string flag: it takes the next argument as its prompt, so the form above puts the empty value attached and last (`-p=`). `--input-format stream-json` requires `--output-format stream-json`. A stream message without `event` or `message` is refused with exit 1 and no model call.
   - **Claude Code.** `--output-format json` prints nothing until the process exits, and `claude -p` does not exit while a `run_in_background` task it started runs, so a CLI that leaves a server running loses its result. With `stream-json --verbose`, the `result` event arrives when the turn ends, whatever is still running. Its fields are the json mode's.
   - **Codex.** `exec resume` has no `-C`; the process's cwd is the worktree, as for every CLI.
   - **Root.** Claude Code refuses `--dangerously-skip-permissions` as root (exit 1, before any request), so a Runner running as root cannot launch it (§3.12).
   - **Open point for CW3 and CW4: Claude Code's inline schema.** `--json-schema` takes the schema JSON inline, as one argv entry. Through an npm `.cmd` shim it passes through cmd.exe, which the batch-argv probe (§3.2) exists to vet; the schema is Runner-built and charset-checked, but it contains quotes and braces. CW3 and CW4 pick one: rely on the batch-argv probe being `verified` (the `.cmd` rule of §3.2 already refuses otherwise); require Claude Code's `.exe` and refuse its `.cmd` shim with a reason; or use a file form, if a Claude Code version offers one. Recommended before CW2: the first, with a CW2 test that round-trips the schema through the probe's quoting. CW2 showed the first cannot work (below): **the second is the decision.**
     - **Settled by CW2 (#225): the first option cannot work, so CW3 and CW4 take the second.** Both Windows launchers refuse any `.cmd` or `.bat` argument containing `" % ! ^ & | < > ( )` or a line break before the batch-argv probe matters: the Job host's `BuildBatchLaunch` (managed-process-job-host.ps1:733) and the portable child's `resolveWindowsArgvLaunch` (portable-process-child.mjs:223). The probe only checks that ordinary values reach a `.cmd` intact. The schema JSON always has quotes, so a `.cmd` Claude Code is refused with a reason ("Claude Code's npm shim can't carry its result schema; install the native claude.exe") in the free checks (CW3) and as a crew rule (CW4), and only its `.exe` is launched. `claude --help` (2.1.326) offers no file form. CW2 pins the refused characters to both launchers' source (`WINDOWS_BATCH_SHIM_UNSAFE_ARGUMENT`).
     - **For CW3: Codex and agy `.cmd` shims and paths.** The same guard refuses a Codex or agy `.cmd` launch whose Runner-built arguments contain one of those characters: a state folder, schema path or worktree under, say, `C:\Program Files (x86)\` or a user folder with `&` or `%`. For a `.cmd` CLI, the free check (CW3) runs `windowsBatchShimRefusedArguments` on an argv built with the real state folder's paths, and CW4 does the same with the project's worktree folder before planning; each reports the refusal before any launch.
     - **If an unsafe `.cmd` launch gets past CW3 and CW4** (a path changed after the checks, or a resume): today the Job host throws an uncoded `InvalidOperationException` ("Unsafe .cmd/.bat argument rejected"), and the portable child an uncoded `Error`. That is not CW5a's coded case 1 (§3.11), so it must not be reached: CW5 runs `windowsBatchShimRefusedArguments` on the exact argv of a `.cmd` CLI right before `ManagedProcessService.start`, and refuses the launch itself with a coded Runner refusal (`cli_launch_argv_unsafe`), handled as case 1 with the CLI's health untouched. Giving the launchers' own refusal a code, so that it reaches case 1 by itself, is a follow-up outside this plan; it is not needed while CW5 checks first.
3. **Environment.** The Runner's child environment for that owner (child-environment.ts), so sensitive names are dropped and the Playwright CLI variables and PATH entries are set (playwright-cli.ts:413-428). The CLI keeps the user's own configuration (its skills, MCP servers, hooks, project instruction files), as when the user runs it. `AIBOARD_MCP_DEPTH` is set to 2 for a CLI process (§3.11).
4. **Wait.** Until the CLI delivers its result, the CLI exits, the attempt's deadline (`maxMinutesPerAttempt`, inside the Build's time budget), or the assignment's abort signal. For Claude Code and agy the result is the stream's `result` event; for Codex it is the exit (its `-o` file is complete only then). A Claude Code process may still be running when its `result` event arrives (a background task keeps it up, §3.5 step 2); the branch takes the result and goes on to the stop without waiting for an exit. A deadline or abort signals the process and then stops the owner (§3.11). Output is read in bounded pages and streamed to Run details as a live tail (live-model-output.ts).
5. **Stop.** Before Collect, the branch runs `closeAgent(owner)`, which stops everything the CLI left running (a dev server, a watcher, the Playwright CLI session), then runs a fresh check of the owner's Playwright folder (`PlaywrightCliSessions.checkOwnerBrowsers`, the check `removeRun` runs for each owner folder: the browsers its profiles name plus its known escapes) (§3.10). Only a verified stop continues. An unverified stop never submits: the attempt returns `stop_unproven`, and #220's scheduler pause keeps the worktree claim (§3.11, case 2). That pause is on main.
6. **Collect.**
   - Undo the CLI's commits (§3.7).
   - Restore any `docs/project/**` change from the baseline and add a concern naming the paths (CWD-7).
   - Compare the project folder's HEAD, index and status with the snapshot taken before the launch. A change is recorded as `projectChangedDuringAttempt` on the attempt and shown to the Architect; it is a fact, not a refusal.
   - Record a durable `worker.cli_attempt_recorded` event: provider, CLI version, model, CLI session id, exit code, outcome or failure kind, the bounded summary, `replacedCliCommits`, `restoredProjectDocs`, `projectChangedDuringAttempt`, token usage when the CLI reported it.
7. **Map the outcome.**
   - `done` → re-run the checks (§3.6), then submit through the shared submit function.
   - `needs_decision` → the shared `ask_architect` path; the loop status is `waiting_for_architect`. After the answer, the next run resumes the CLI session with the Architect's guidance from the new context pack.
   - `cannot_do` → the shared `request_replan` path.
   - No result, or an unreadable one → a CLI failure (§3.8).
   - A failure → `suspended` with `provider_error`, which the driver's existing failover handles (native-worker-driver.ts:586-616).
8. **Shared lifecycle functions.** The bodies of `submit_task` (worker-runtime.ts:343-469), `ask_architect` and `request_replan` (worker-lifecycle-tools.ts:302, :357) move into functions both paths call. The API worker's tools call them unchanged, so their tests stay as they are.
9. **Usage.** One budget-ledger entry per CLI run: tokens when the CLI reports them, cost 0 under `account_not_metered`. The USD cap does not bind CLI work; the time limits do (CWD-5). Re-runs count as validation time, as any worker's evidence commands do.
10. **Restart.** After a Runner restart, the driver runs the persisted assignment again (native-worker-driver.ts:329-337). For a CLI it starts a new process that resumes the recorded CLI session, or starts fresh with the handoff section when none was recorded. The previous process's residue is reconciled by the existing startup recovery; nothing new. Before the attempt runs again, the restart path calls `retryStop` (task-scheduler.ts:390-404, on main since #220). An attempt whose CLI had already exited, recorded with `collected: false` (§3.11, case 2), never starts a new CLI process: it goes straight to Collect.

### 3.6 Runner re-runs for evidence
The CLI's checks are claims. The Runner re-runs each one, after the CLI stopped and after §3.5 step 6, so the evidence matches the tree it submits (change-set.ts:130-136).
- Each check runs through the same path as `run_evidence_command` (evidence-tools.ts:147): one executable with arguments, no shell, cwd inside the worktree, with its `outputs` kept as artifacts (VF6). The record's actor is the assigned worker and its attempt (evidence-store.ts:126-137), so the submission rule holds (acceptance-contracts.ts:302-306), and the fact carries `source: "runner_rerun_of_cli_claim"`, so the Architect sees who ran it.
- A check whose executable is missing is `not_run: tool_missing` through VF2's lookup, never a failure.
- A check that is a shell line (`a && b`, pipes, redirection) is not run; the result lists it as "not re-run: shell line" and the next prompt asks for single commands.
- Each re-run gets the task's remaining validation budget as its timeout, at least 1 minute and at most 10. The budget is per task across attempts and advisory, as it is for every worker (validation-budget.ts), so a spent one still gives each re-run a minute and every reported check leaves a record. A re-run the budget cut short (its timeout below the 10-minute cap) that times out is `not_run: validation_budget_spent`, never a failure and never support: a timeout says nothing about the work (a hang the CLI introduced looks the same). Its record is kept and reported to the Architect like the other `not_run` reasons. A criterion it was the only check for is a gap, so the CLI gets its fix round, whose prompt asks for a narrower check. If the criterion is still cut short after the fix round, the work is submitted with a concern naming it "Not verified by the Runner", linked to the timed-out record (a timeout, not a pass), so the budget alone never fails the attempt. A timeout at the cap is the check's own: a long suite, such as this repository's `npm run test:runner-v2` (hours), times out and fails. The Runner names no project command; the preamble asks for targeted checks (2026-11-03 plan §6.5; principle 1 of the verification plan).
- **Every check runs on the tree the CLI left.** The Runner persists that tree (`reruns-pending.json` in the session's CLI folder) before the first re-run. Files a re-run changes are restored right after it, before the next check runs, and the fix-round prompt names them. A pass supports a criterion only when its record's working-tree identity is known and equals that tree, so a check that changed files (a formatter, a code generator, an install) supports nothing. A change only under the Playwright CLI output folder (`.aiboard-browser/`, where a browser check writes what it keeps in `outputs`) is restored too, but it is not a change to the CLI's work: such a re-run supports its criteria when its record shows it began on the CLI's tree. Re-runs run in CW8's re-run browser session, whose stop is proven before anything is submitted. A Runner that stops during the re-runs restores the persisted tree on its next entry and runs them again, starting no CLI.
- A re-run counts only when its executor verified its processes gone. **A stop the re-runs leave unproven holds the attempt**: a re-run whose cleanup is not verified (returned or thrown), a broker `tool_timeout` (the broker stopped waiting; the command may still run), or a re-run browser session whose stop is not proven. Nothing is submitted: the attempt returns `stop_unproven` with the kept outcome `{ type: "paused", reason: "cli_reruns_pending:<taskId>" }`, the scheduler keeps the worktree claim and pauses (#220), and once its retried stop is proven the Resume re-enters the same attempt, which restores the persisted tree and runs the re-runs again, starting no CLI (as `cli_collect_pending` does for a collect). Any other error out of the re-runs proves the owner's stop first (`proveCliStop`: the owner's managed processes through `closeAgent`, then the owner folder's browser check), holds the attempt the same way when that stop is unproven, and otherwise puts the persisted tree back and fails the attempt with `cli_checks_rerun_failed`. A re-run is a one-shot command, which `closeAgent` does not cover; the executor's own cleanup proof covers it, which is why a `tool_timeout` is held rather than taken as stopped.
- **Criterion links.** A check with `criterionIds` links its evidence to those criteria. When a criterion has no linked supporting re-run, or any re-run failed (linked to a criterion or not), the CLI gets a **fix round**: its session resumes with the re-run results and the missing criteria. One fix round by default (CWD-3). The fix round stays pending until a run launched with it delivers a `done` (a question or a provider failure in between keeps it), and it runs inside the deadline of the run it follows, so a gap never gives the attempt a second time limit (CWD-6); a run after a question or a provider failure gets its own limit, as any run after a question does. After the fix round, a criterion still without support fails the attempt with `cli_checks_failing` (a failed re-run is linked to it) or `cli_checks_unsupported`, and the existing attempt rules requeue the task (another worker, demotion after two failed attempts, native-worker-driver.ts:913-941). A re-run that still fails after the fix round while no criterion depends on it (each criterion it names has another passing re-run, or it names none and the criteria are supported) does not fail the attempt: the work is submitted with the failure as a known defect in `unresolvedConcerns`, beside any "Not verified by the Runner" criterion.
- The CLI's `summary`, `notRun` and `concerns` become the submission's summary and `unresolvedConcerns`, and the validation-scope claim, marked as the CLI's report.

### 3.7 Commit handling
At Full access the CLI can commit on the task branch, because the worktree's HEAD is that branch; "do not commit" is only a prompt rule.
- Before the launch, the Runner records the branch tip: the baseline, or its own last commit on that worktree. It takes that commit from its own state (the workspace-owner record), never from HEAD, so a commit an earlier CLI run left is after the tip and is undone too.
- Before the launch, the Runner also refuses to start a CLI in a worktree that is detached, on another branch or in an unsettled operation (an earlier CLI left it so): the attempt fails with the same `cli_history_rewritten` code, and no CLI is started.
- After the stop, a new WorkspaceManager method `undoForeignCommits(workspace, recordedTip)`:
  - refuses an unsettled merge, rebase, cherry-pick or revert (the same list as workspace-manager.ts:335-338);
  - refuses when HEAD is detached, is not the task branch, or `recordedTip` is not an ancestor of HEAD (the CLI rewrote history or switched branches), and when a commit after `recordedTip` is a merge (history from outside the task branch): the attempt fails with `cli_history_rewritten:<kind>`, which the Architect sees, nothing is submitted, and the worktree is kept as the CLI left it, its files included. A rewritten or merged history fails that attempt only. A worktree left off the task branch is refused before every later launch, so the failure tells the Architect to replan the work as a new task (a new worktree);
  - otherwise moves the branch back to `recordedTip` with a compare-and-set `update-ref` and leaves the index and working files as they are, so the whole change goes through the guarded commit and its secret check;
  - reports the number of replaced commits as `replacedCliCommits`.
- SB4b reuses this method for its model-commit fold-back (2026-11-03 plan §12.3); it gets a filesystem-owner review entry like WorkspaceManager's other methods.
- Pushes, tags and other refs the CLI created are outside the worktree's commit. The preamble forbids them; the Runner cannot stop them at Full access (§6, risk 6).

### 3.8 Failure mapping and cooldowns
Each adapter classifies a CLI failure into a `ProviderFailure` (provider-health.ts:10-15). The driver then records it, cools the provider down and fails over exactly as for an API worker.

| CLI signal | Kind | Cooldown |
|---|---|---|
| Codex "You've hit your usage limit" (prose, exit 1, the `-o` file empty; owner logs); agy exit 3 with "Resets in 4h53m36s" or a weekly cap; agy `/quota` with a `remaining_fraction` of 0 and its `reset_time` (free checks and Test); Claude Code `is_error` with a usage-limit message, or a `rate_limit_event` with `status: "rejected"` and its `resetsAt` | `usage_limit` | the stated reset, else 1 h |
| `codex login status` (exit 1, "Not logged in" on stderr) or `claude auth status` (exit 1, `loggedIn: false`) not logged in; Claude Code's result "Not logged in · Please run /login" (`is_error`, exit 1); agy `models` failing with a login message; an auth error in the run | `authentication` | 24 h, ended by a passing Test |
| The model is not available: Codex "The '<model>' model is not supported when using Codex with a ChatGPT account." (an `error` event and `turn.failed`, exit 1); Claude Code `is_error` with `api_error_status` 404 and `api_error_type` `not_found_error`; agy refusing the model or its effort ("invalid model selection (--model … --effort …)", exit 1, no model call) | `authentication` | 24 h, ended by a passing Test: the owner must fix the setup |
| A rate-limit (429) message | `rate_limit` | 1 min |
| A server error or overload message | `provider_unavailable` | 5 min |
| A crash, a non-zero exit with no result, or an unreadable result | `transient` | 30 s after two in a row |
| The executable is gone mid-Build | `authentication` | 24 h, ended by a passing Test |
| The attempt's deadline, or the Build was cancelled | not a provider failure: the attempt fails, or `cancelled` | — |

- A reset time counts only when the CLI stated it (a duration or a clock time in its own output). It sets `retryAfterMs`. agy's `retryable: true` is ignored. A guessed reset never sets one (2026-11-03 plan §5.5).
- Mapping a model error to `authentication` rather than `invalid_request` is deliberate: `invalid_request` never fails over (native-worker-driver.ts:943-945), and a mistyped CLI model should hand the task to another worker, not fail it.
- Patterns are pinned against fixtures captured from real output in CW0 (runner-v2/test/fixtures/cli-workers/). A message no pattern matches is `transient`, never a silent success.
- What CW0 found about the signals:
  - Codex writes its `-o` file even when the turn fails or is killed; it is then 0 bytes. "No result" means an empty or unparsable file, never a missing one.
  - A Codex `error` event or item is not always fatal: a model-metadata warning and reconnect notices come as `error` too. Only `turn.failed` ends the turn.
  - No fixture exists yet for a real usage limit from any CLI, a 429, a 5xx or overload message, or agy logged out. Those rows are pinned from the owner's logs (CW2), and an unknown message stays `transient`.

### 3.9 Handoff in both directions
Failover keeps the task, the attempt, the worktree and the session id (native-worker-driver.ts:331-337, :613-615). An API worker that takes over from another API worker inherits the conversation. Across a CLI boundary neither side can read the other's conversation, so the Runner writes a handoff summary from facts it holds.
- **API → CLI** (and CLI → another CLI): the CLI prompt gets an "Earlier work on this task" section: the previous worker and why it stopped; its last assistant text or CLI summary, at most 2,000 characters; the changed files with line counts from `git diff --numstat <baseline>` in the worktree; the evidence ids already recorded for this attempt; and "do not repeat completed work".
- **CLI → API**: the driver adds one continuation message, built from the latest `worker.cli_attempt_recorded` event, with the same fields. The API worker then continues on the existing resume path (native-worker-driver.ts:881-901).
- **The same CLI again**, after its cooldown or a fix round: the recorded CLI session resumes (§3.5 step 2), so that CLI keeps its own context.
- The handoff summary is a claim, labelled as written by the previous worker; the file list and evidence ids are facts.

### 3.10 Browsing
CLI workers browse like every other role, with the Playwright CLI the Runner ships (VF7b, VD-6). The Runner trusts only what it re-runs and its own final check (verification plan §4.8).
- A CLI cannot run the Runner's `process.start`, and a session it started from its own shell is not recognized as the session process, so on POSIX its browser is checked only at the run's removal (verification plan §9, VF7b item 6b). So the Runner starts the worker owner's session, `playwright-cli-session`, as a managed process for that owner before it launches the CLI, when the inventory recorded a browser the CLI can use (CWD-2). The CLI's `playwright-cli` commands then reach it through the environment and PATH the Runner sets for the owner (playwright-cli.ts:413-428).
- The preamble says the session is running, points to the AIBoard skill file the Runner ships for it (runner-v2/skills/playwright-cli/SKILL.md, by its absolute path in the Runner install), and asks for screenshots and snapshots as check `outputs`, so a re-run keeps them as evidence (VF6).
- The session stops with the owner (§3.5 step 5), with VF7b's POSIX browser check unchanged. Session ownership is unchanged: it is the same owner the CLI runs as.
- After that stop, the driver runs a fresh check of the owner's Playwright folder (`PlaywrightCliSessions.checkOwnerBrowsers`, the check `removeRun` runs for each owner folder: the browsers its profiles name plus its known escapes). It does not read a stop's browser record, as the final check does (`PlaywrightCliSessions.cleanupAfterStop`, §2.7): reading afresh never depends on which stop recorded what, and a known escape stays `escaped` until a later check proves it gone. `escaped` or `unknown` means the stop is not proven: case 2 of §3.11. The browser is never signalled. The stop's pause reason names the PIDs of the browsers still running, which the owner stops before Resume.
- `playwright-cli` exits 1 when a command fails (§2.7), so a re-run of a failed browser check fails as evidence instead of passing on exit 0.
- The CLI's own server, if it started one, stops when the attempt stops. The Architect can start the app in its own copy during review (VF5).

### 3.11 Process ownership and cleanup
No fencing rule changes. A CLI attempt whose stop is not proven keeps its worktree claim (case 2 below), through the claim-keeping pause #220 put on main for every worker. A CLI is one more managed process; what is new is that it starts many descendants.
- **Ownership.** The CLI is started by `ManagedProcessService.start` for the worker's owner, so it runs in the backend's containment: a Windows job object, or a POSIX process group under the portable supervisor. Its descendants (shells, test runners, MCP servers, dev servers) inherit it.
- **Stop.** After every exit, deadline, abort or Runner shutdown, `closeAgent(owner)` stops the owner's processes, and the attempt continues only on a verified stop. Nothing outside the owned containment is ever signalled, and the host's processes are never enumerated (DECISION 2026-09-19 §8).
- **Escapes.** A POSIX descendant that leaves the process group (setsid, daemonizing) is outside what the Runner can prove or stop, as for a command an API worker starts at Full access today. A Windows descendant created outside the Runner's Job is the same. The rule: a CLI whose processes leave the containment by design, or whose behavior on an OS was not measured, is refused on that OS until a design amendment, which fails closed. CW0 measured it (docs/runner-v2/cli-workers-spike-2026-11-17.md §6), and the owner decided v1 as follows (CWD-10, CWD-11):

  | CLI | Windows | Linux | macOS |
  |---|---|---|---|
  | Codex CLI | **refused until CW0b** explains the Job escape and a fix lands: in 3 of 7 CW0 runs a process Codex started (a `Start-Process` server through the Store `pwsh.exe`, a plugin hook) was alive outside the Job after a verified stop | **refused**: every shell command runs as `/bin/sh -lc` in a new session, and `codex-code-mode` and `git` in their own process groups (measured) | **refused**: not measured; the same POSIX launch code is likely, so it fails closed |
  | Claude Code | allowed: nothing found outside the Job | **refused**: every Bash tool command runs as `bash -c` in a new session (measured) | **refused**: not measured; fails closed |
  | agy | allowed: nothing found outside the Job | **refused until measured** | **refused until measured** |

  - The refusal is a crew rule (CW4) and a free-check result (CW3), with a reason per CLI and OS, for example "Codex CLI workers are not available on Linux: Codex runs its commands outside the process group AIBoard can stop." A refused CLI is listed in Settings with that reason and cannot be picked in the crew picker.
  - Coordinator's reading (fail-closed; the owner can overrule): the agy rows. Nobody measured agy on POSIX, so it is refused there until a measurement.
  - Lifting the POSIX refusals is a separate follow-up plan: containment by cgroup v2 on Linux (the `contained_workload` adapter that docs/runner-v2/posix-detached-descendants.md names). macOS needs its own measurement and design.
  - Lifting the Codex refusal on Windows needs CW0b's explanation and a Runner fix in its own packet, with an independent review. Coordinator addition: then a CW0-style measurement with the fix in place.
- **Windows needs a verified Job (CW3 review, 2026-11-18).** The Windows allowances above were measured under the Job. On a Windows host whose `jobContainment` fact is not `verified`, the execution host falls back to the portable supervisor (execution-host.ts, `jobObjects: "unavailable"`), which cannot stop what an agent session leaves behind. So a CLI worker on Windows needs verified Job containment. The free check reports such a host's CLIs as unavailable (`job_containment_unavailable`, with its reason) and launches nothing, a Test is refused with 409, and CW4's pre-planning check therefore marks the CLI unhealthy before any task is assigned. CW5's launch must enforce the same rule at the launch itself.
- **Recursion.** The CLI process gets `AIBOARD_MCP_DEPTH=2`, the local MCP door's limit (child-environment.ts:87), instead of the Runner's depth + 1. So a user-configured `aiboard mcp serve` inside the CLI refuses with `local_mcp_recursion_limit` (local-stdio-mcp.ts:104-105), and a later `aiboard exec` refuses by depth (2026-11-03 plan §11.4), and no AIBoard → CLI → AIBoard loop forms. It is a Runner-set value: a tool cannot override it (child-environment.ts:170). This binds cooperating processes only, like every depth rule.
- **Review.** CW5a, CW5 and CW8 touch process ownership: each gets an independent review, recorded in its pull request, and keeps the affected portable coverage. CW5's review covers how the CLI branch reaches #220's claim-keeping pause (case 2).
- **A Runner failure is not a CLI failure.** A launch, stop or browser session start the Runner cannot prove (a fence claim that runs out of time, a launch blocker, an unknown descendant inspection, a session start that fails its wait) is recorded on the attempt as the Runner's own failure. It never goes to the CLI's provider health, so it never cools a CLI down or fails its task over to another worker.
- **What main does today (#220).** A driver whose attempt's stop is unproven returns `stop_unproven` with the outcome it had, or throws an error `isProcessStopUnprovenError` classifies. The scheduler then keeps the packet claim, appends `worker.stop_unproven`, and pauses with `process_stop_unproven:<taskId>`; the task stays `running` (task-scheduler.ts:554-569, :580-591, :777-830). On resume, before any Architect turn, it calls the driver's `retryStop`: a proven stop records the kept outcome through `recordOutcome`'s own release and appends `worker.stop_proven`, and a stop still unproven pauses again (task-scheduler.ts:832-951). Every other pause and failure still releases the claim as `"stopped_fenced"` (task-scheduler.ts:743-768), and a recorded failure gives the Architect `task_failure_resolution_required` (build-runtime.ts:2132-2142). The CLI design uses this mechanism and changes nothing in the scheduler.
- **Case 1: the launch is not proven and nothing started.** For example, the fence claim at launch runs out of its 15 s deadline, a launch blocker refuses the start, or (after CW5a) the host refuses a `.cmd` launch before any spawn (§3.2). CW5 treats a start failure as case 1 only when it carries a Runner launch-refusal code (such as CW5a's `windows_batch_argv_unverified`, a launch blocker or a fence claim deadline) and `isProcessStopUnprovenError` does not classify it, which means the managed start proved its own cleanup. It never decides from message text. Anything the classifier marks, an unverified-cleanup `AggregateError` included, is case 2 on main today, even when its first error is a refusal; until CW5a lands, that is what a refused `.cmd` launch gets. The attempt ends `failed` with `process_launch_unproven:<code>`, and the CLI's health is untouched. The claim release is correct here, because no process ran. The Architect gets the failed task as for any failure and can retry it. With health untouched and the task's affinity kept, a retry usually goes to the same CLI, which is right, because the CLI did not fail. A second `process_launch_unproven` in the same run pauses the run with `process_launch_unproven_repeated:<code>` instead of failing again. On a loaded host the owner sees the cause in "Needs you" instead of attempts being spent.
- **Case 2: the stop is not proven.** The CLI or something it started may still be running and writing to the worktree. Nothing is submitted. The branch uses #220's mechanism; the scheduler needs no change.
  - If the CLI had delivered its result or exited (or its deadline signalled it) before the unproven stop, the branch first records `worker.cli_attempt_recorded` with `collected: false`. Since CW0, a delivered result is the normal case for Claude Code and agy: their `result` event ends the turn (§3.5 step 4), and a Claude Code process with a background task is still running when the stop starts. The branch writes that event to the result file in the Runner-owned folder, so it has a digest like Codex's `-o` file. The record holds the CLI's exit code (none when it was still running), its result file's digest, the deadline, if any, and the worktree as the CLI left it (HEAD, and a tree hash of the working files built in a temporary index, `GIT_INDEX_FILE` with `git add -A` and `git write-tree`, which writes only objects and leaves the worktree's own index alone). It then returns `stop_unproven` with `reason` naming the CLI's exit or deadline and the stop failure, and with the kept outcome `{ type: "paused", reason: "cli_collect_pending:<taskId>" }`. The generic `worker.stop_unproven` is the stop's event; no CLI-specific stop event is needed, because the CLI facts are in `reason` and in `worker.cli_attempt_recorded`.
  - `retryStop` is the driver's own (native-worker-driver.ts:259-296), which already stops the owner's managed processes, MCP servers, language servers and subagents. The CLI branch adds one check: the owner-folder browser check must not be `escaped` or `unknown` (§3.10), or the retry throws and the run stays paused.
  - On a proven retry, #220 records the kept `paused` outcome: it releases the claim as `"stopped_fenced"` and pauses the run once more with `cli_collect_pending:<taskId>`. The next Resume runs the same attempt again. The branch finds the `collected: false` record, checks the result file's digest, and checks that the worktree still matches what the CLI left: the same HEAD and the same tree hash, built the same way. It starts no CLI process, and continues from Collect (§3.5 step 6) with the outcome the CLI reported. A mismatch collects nothing and fails the attempt with `cli_collect_worktree_changed`, which names what differs.
  - Between the two Resumes the claim is released, but the run is paused, so nothing else starts in that scope. On the second Resume the Architect may act before the attempt runs again, for example by steering or cancelling the task. Then nothing is collected, and the CLI's work stays in its worktree for the handoff (§3.9).
  - So resuming such a run takes two Resumes: one proves the stop, one collects. It is the rare path, and it keeps the scheduler unchanged; folding the two into one would need the scheduler to know about CLI collection.
  - An unproven stop while the CLI was still running without having delivered a result (a deadline or abort mid-turn) keeps the outcome `{ type: "failed", reason: "process_stop_unproven" }` as the driver's wrapper does, after a proven retry the existing failure path applies, and the CLI's health is untouched.
  - Retrying the task on another worker while a stray process may still write is the risk this case exists to prevent; #220's kept claim prevents it.
- **Case 3: the browser session start fails.** For example, the `until.pattern` evaluation hits its wall ceiling on a busy host (§3.11a). The run does not pause. The failure is recorded on the attempt, the CLI runs without a browser and the preamble says so, and the CLI's browser checks are `not_run`. The start is never retried with a longer bound.

### 3.11b CW5a: a launch refused before any spawn is never started
- **The rule.** When a launch is refused before it spawns anything, the managed record reaches `stopped` through `stopExact`'s proven stop, which finds nothing to stop, and `ManagedProcessService.start` throws only the refusal, with its code. No `AggregateError` is thrown. The runtime's detach is not blocked (managed-process.ts:149).
- **First, prove it.** Before the change, the packet proves that nothing exists before the refusal on both paths that call `assertWindowsBatchSemantics`: the Windows Job path (windows-process-backend.ts:111) and the native path (:67). That means no process, no fence authority, no state directory or file that would need a stop. If either path creates something first, the refusal moves before it, or that path keeps today's behavior. The packet never marks a record stopped while something of its launch can exist.
- **Scope.** Only refusals raised before any spawn and before any streaming launch state, each with a code. The backends create nothing before `assertWindowsBatchSemantics`, but the streaming runtime above them durably begins the launch (a host-launch record, an isolation lease and a pending launch effect) before it calls the backend, and that cleanup cannot be proven. So the managed runtime applies the same rule (`assertWindowsBatchLaunchAvailable`) to the path it resolved, for a full `process_group` launch, before `run.openStreaming` (execution-host-managed-transport.ts). Any other start failure keeps today's `stopExact` and its aggregate. A list or signal of such a record answers from the record: it is `stopped`, pid 0, with no streaming session and no unreleased host launch.
- **Classification.** The refusal `ManagedProcessService.start` then throws carries no `process_cleanup_unverified` code and no cause that has one, so `isProcessStopUnprovenError` (process-stop-proof.ts:51-58) does not classify it and #220 does not pause for it. Until CW5a lands, the aggregate is classified, so main pauses with the claim kept, which is fail-closed.
- **Ownership.** This changes process-ownership bookkeeping, so it gets an independent review recorded in its pull request, a Windows test (a real refused `.cmd` launch on a host whose batch-argv fact is not `verified`, a `.cmd` that still runs when the fact is `verified`, and list and signal of the refused record), a portable test (list and signal of a never-started record after a command-not-found start, alone and beside a live process) and an in-memory test (a fake runtime that refuses after creating state, which keeps the aggregate).

### 3.13 Crew rules
- CLI runtimes are workers only. The factory refuses a CLI runtime as Architect or reviewer with `cli_runtime_role_refused`, and leaves CLI runtimes out of the Architect and verifier routers and the verifier list (native-build-factory.ts:1236-1248; lib/client/native-build-engine.ts:518). No `AgentModel` is built for them (native-build-factory.ts:1263-1270); the driver's CLI branch runs before its model lookup (native-worker-driver.ts:355-359).
- A crew of only CLI workers is allowed; the Architect is an API model.
- Capabilities: a CLI runtime declares the worker capabilities a task can require; image input is off (the prompt is text).

## 6. Risks
1. **CLI output drifts.** All three CLIs changed versions within three days on this PC. Parsers keep to documented JSON fields where they exist, record the CLI version on every attempt, and fail to `transient` on anything unknown, never to success. The Test button shows a broken parser at once.
2. **Quota messages are prose.** Codex reports its usage limit only as prose with exit 1, and agy marks even its weekly cap retryable (2026-11-03 plan §2.1, owner logs). A missed pattern costs a 30 s cooldown and a retry, not a wrong result; CW0's fixtures pin the known ones.
3. **Descendants that leave the containment.** The Runner cannot prove them stopped. CW0 measured it: Codex and Claude Code leave the process group by design on Linux, and Codex left the Job on Windows in 3 of 7 runs, so v1 refuses those, and every unmeasured CLI and OS (§3.11). The observer CW0 used misses a child whose parent exits between two samples, so "nothing found" for Claude Code and agy on Windows is a finding, not a proof.
4. **Tests run twice.** The CLI runs its checks, then the Runner re-runs them. This is the price of recording facts; the preamble asks for targeted checks, and re-runs are bounded by the validation budget.
5. **Prompt rules a CLI ignores.** At Full access a CLI can commit, push, edit `docs/project`, or write outside the worktree. Commits are undone, `docs/project` is restored, the project folder is compared, and the secret check runs on the whole change. Pushes and writes elsewhere are disclosed, not prevented (OD-36).
6. **Credentials in reach.** A Full-access CLI runs as the user and can read the user's files, as an API worker's shell can at Full. AIBoard adds no credential to its environment, and drops sensitive names from it (child-environment.ts:302-305).
7. **The user's own CLI configuration.** Hooks, plugins and MCP servers the user configured run inside Builds. That is how the user runs the CLI (OD-35); the depth rule keeps AIBoard's own MCP door out.
8. **USD budgets.** CLI use is unmetered, so a USD cap does not bind it. The crew picker says so; the time limits apply.
9. **Process edges under more load.** A fence claim that waits out its 15 s deadline behind another holder, the `until.pattern` wall ceiling on a busy host, and the Windows launch cleanup's unfenced `handledControl` read (§3.11a) all fail closed. The cost is attempts that fail (case 1), runs that pause (cases 1 and 2), or attempts that run without a browser (case 3), not unowned processes. CW0 measures how often fence claims fail on the new lock; a fix is a fencing change with its own review, outside this plan.
10. **Vendor terms.** Settled by OD-35: each CLI is used as its vendor supports, for delegated work, with the user's own CLI and login, on the user's machine, never over Remote.
11. **The `"stopped_fenced"` release after a thrown cleanup error (resolved by #220).** Before #220, any error a worker driver threw, `process_cleanup_unverified` included, was recorded as `failed`, and recording it released the packet claim as `"stopped_fenced"`, so a stop nobody proved was labelled stopped. That was fail-open. #220 fixed it for every worker: a classified error, or a `stop_unproven` outcome, keeps the claim and pauses (§2.8). CW5 builds on it and adds only the CLI side (case 2).
