# Runner V2 filesystem owner review — 2026-11-17, CW1 (CLI worker configs beside the provider envelope)

Scope: the CW1 change to the reviewed owner `runner-v2/src/encrypted-provider-config-store.ts` (packet CW1 of `docs/plans/2026-11-14-cli-workers.md`, §3.1). Source references are relative to `runner-v2/src/`. This is a static review of the change, not a sandbox. The regression coverage is in `runner-v2/test/cli-worker-config.test.ts` ("the encrypted provider store keeps cli configs in a plain sidecar ..."). The entry in `runner-v2/test/filesystem-mutation-routing.test.ts` refers to this record.

Why it changed: the store validates the whole decrypted array on load, and a Runner from before CW1 refuses the `cli` transport. With a `cli` config inside the envelope, a rolled-back Runner could not load any provider config. A re-push could not repair it either, because the PUT route loads the stored configs first. CLI worker configs hold no secret, so they now live beside the envelope in plain JSON, and an older Runner never reads that file.

It holds only a runtime id, a CLI provider id, a charset-checked model id and effort, capabilities and a priority, and `validateProviderConfigs` refuses a `cli` config with any secret, base URL, token or secret source, so a hand-edited secret is dropped at load. (b) A process of the same user can edit the sidecar, as it can edit any per-user state. The worst case is a CLI worker config with charset-checked arguments; the envelope's keyed configs are unaffected. (c) The two writes are not one transaction. A crash between them leaves the old CLI worker list with the new keyed list; it never mixes a key into the sidecar. |
