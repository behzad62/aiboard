# Runner V2 filesystem owner review — 2026-11-18, Windows Job host record retention

Scope: the retention change to the reviewed owner `runner-v2/src/windows-job-process-host.ts`, and its caller in `runner-v2/src/execution-host.ts` (run binding close) with the collector `releasedWindowsJobRecords` in `runner-v2/src/inspection-cleanup.ts`. Source references are relative to `runner-v2/src/`. This is a static review of the change, not a sandbox. The regression coverage is in `runner-v2/test/windows-job-record-retention.test.ts`, the close wiring test in `runner-v2/test/execution-host.test.ts` ("run binding close hands Job-host record retention ..."), and the real-host pin in `runner-v2/test/windows-job-real-host-guarantees.test.ts` ("a settled run close deletes its released Job records ..."). The entry in `runner-v2/test/filesystem-mutation-routing.test.ts` refers to this record.

Why it changed: the shared Job host (`<state>/managed-processes-job-host`) only marked a released process as released (`releaseOwned`, the `backendOwnershipReleasedAt` tombstone). Its `<processId>.json` record and its `<processId>/` folder, with the raw `stdout.log` and `stderr.log` of every worker shell, stayed forever. The constructor and every run-end spare sweep read every record, so startup and run close slowed as Builds accumulated, and command output that may hold secrets had no retention rule.

Bounded scans: the constructor reads at most `maxRecordScan` record files (default 512) before it returns. The records past that slice get the same startup crash recovery (unclaimed spares dropped, claim-window pairs retired and kept as their audit trail) in background batches of the same size, with the event loop free between them, so no recovery duty of the old full scan is dropped. Each run-end spare sweep reads at most `maxRecordScan` files, in name order from where the previous sweep stopped (`nextRecordNames`). Listing names is still proportional to the directory; the limit bounds the files read and parsed. The spare-recovery deletions (`removeSpareFiles`) are unchanged.

The constructor's bounded slice still refuses startup on a record file it cannot read, as before; a record past the slice that cannot be read is skipped by the background batches, as a run-end sweep skips it.

Records written before this change: only a later settled close of the same run names them, so on an existing install they stay until then (a run that never closes again keeps them). Every startup still recovers them, now past the first slice in the background. A one-time cleanup of them would need its own proof that nothing owns them and is out of scope here.

Private Job hosts (CW3): a transient run (`<state>/transient-runs/<runId>/job-host`) and a historical Git inspection each get their own Job host, whose whole folder is removed after the binding's proven close. Retention never runs for those bindings (`jobRecordRetention` is passed only for the shared host): their removal already covers the records, and the transient release's `awaitSupervisorsExited` finds supervisors through that host's in-memory records, which retention would otherwise drop. Their scans are trivially bounded: each private host starts on a new, empty folder and has no spares.

Second review round (after merging main with CW3):
- Before deleting a folder, the record's supervisor PID must be gone. A pass first proves and marks every named record (deleting those whose supervisor already exited), then waits for the rest together under one deadline per pass: 25 ms polls, 15 s ceiling, the measured basis of CW3's transient supervisor wait, never one ceiling per record. The PID only gates deletion; nothing is ever signalled. A supervisor still alive at the deadline leaves its record marked. A reused PID (EPERM counts as alive) keeps the record, with its raw output, until that process exits; that fails closed. A sweep or startup recovery finishes marked records only once the supervisor is gone, and never waits for it.
- Startup recovery also finishes records a previous Runner's retention pass marked.
- A run-end sweep always includes the spares this host started for the closing run, whatever its window.
- Only one retention pass works on a process id at a time; a second keeps it.
- Unreadable record files skipped by the background startup batches are named once in a warning.
- `windows-job-record-retention.test.ts` runs in PR CI (the deterministic portable contract step); it adds pins for a folder removal that fails after the mark (Windows), retention behind a held fence lock, a release replay racing retention, and the shared wait deadline.
