## Findings

### F1 — High: state and device roots can resolve into the project

Direct start obtains absolute paths using resolve (runner-start.ts:890 and runner-start.ts:1038), compares state and project with lexical relative paths (runner-start.ts:193 and runner-start.ts:1059), then creates state/artifacts (runner-start.ts:212 and runner-start.ts:235). Without a launcher handshake, this path does not run the launcher-only realpath check at runner-start.ts:177. For example, an externally named --state-dir symlink or junction to a directory in the project passes that lexical comparison; the following state writes land in the project. The later ExecutionHost check also uses resolve and relative rather than filesystem realpaths (execution-host.ts:197 and execution-host.ts:953). For remote startup, canonical roots are checked at runner-owned-roots.ts:23 but an overlap is deliberately classified as remoteOnly (runner-start.ts:161), and the start path permits that case (runner-start.ts:185 and runner-start.ts:193). Launcher preparation normally resolves existing ancestors and rejects nesting, but explicitly permits it for that remote-only case (launcher-instance.ts:74, launcher-instance.ts:98, launcher.ts:219 and launcher.ts:227). Checking a root before use also does not pin later child components against a swap.

The class-3 state/device writers affected are build-user-media.ts (manifests, prepared evidence and cleanup), chat-agent-session.ts (session files), credential-migration.ts (journal/pointer/generations), extension-mcp.ts (discovery run cleanup), extension-run-bindings.ts (binding), launcher-instance.ts (launcher files and state preparation), launcher.ts (peer files), proven-snapshot-links.ts (run proof log), remote-admission-store.ts (database parent), remote-audit-store.ts (database parent), remote-device-store.ts (device records and keys), remote-principal.ts (principal and device-policy parents), remote-service.ts (status), runner-start.ts (state/artifacts), storage-key.ts (storage key), and toolbench-session.ts (session files). Their individual call and construction sites are in the table. Direct non-remote aliasing affects local-agent state writers; remote-only nesting affects the remote stores and launcher state. The local-agent guards limit some remote-only actions, but startup recovery still runs for chat and ToolBench (runner-start.ts:419 and runner-start.ts:421).

Suggested fix: before any direct-start write, resolve project and future state/device roots through existing ancestors, reject project overlap for operations governed by this audit, and revalidate/pin parent identities for later writes and cleanup. If nested remote-only state is a deliberate product requirement, give it an explicit project-path policy and keep these modules out of the private set until the requested boundary is met. Do not treat a lexical state name as proof of canonical confinement.

### F2 — High: extension-home containment is lexical at the write boundary

runner-start.ts:215 compares the configured extension home lexically. ExtensionManagementService.open resolves the project but only applies resolve to home before isWithin (extension-management-service.ts:215 and extension-sources.ts:282). An external-looking --extensions-home symlink/junction to a project directory can therefore pass those checks. Remote-only startup also deliberately allows a nested extension home. No canonical parent or descriptor-bound check is performed at the affected writes.

The class-3 extension-home writers affected are extension-management-service.ts (uploads), extension-mcp-launcher.ts (launcher and secrets), extension-mcp.ts (install/runtime and policy files), extension-package-store.ts (package staging and collection), extension-registry.ts (registry and lock), and extension-sources.ts (Git scratch). See each table row for its call sites. Suggested fix: canonicalize the project and future extension home before service startup, reject overlap under this audit's rule, and revalidate/pin the owned home and child parents before mutations. Preserve validated archive-relative path checks; they do not establish the home boundary.

### F3 — Medium: report cleanup targets the checkout

Delivery cleanup is intentionally left off both lists. At review time the coordinator's in-progress change resolves the checkout and each report parent, checks lexical and canonical containment, refuses a non-regular leaf, then removes the canonical-parent/basename path (delivery-execution.ts:847). This is stronger than the original lexical-only check, including for an existing junction in the parent chain. It still uses separate realpath/lstat/rm operations, so a concurrent parent/leaf replacement is not descriptor-pinned; an alphanumeric report basename and a regular file do not prove that this run created the existing leaf. Suggested fix: finish the coordinator's canonical-parent change and couple cleanup to a recorded creation identity, with race-safe parent/leaf revalidation or a platform primitive that binds removal to the verified object.

### F4 — High: existing fixed leaves can redirect or replace writes

chat-agent-session.ts:334, extension-mcp.ts:522 and extension-mcp.ts:834, extension-run-bindings.ts:104, toolbench-session.ts:129 and toolbench-session.ts:160 use fixed temporary filenames with ordinary writeFile, which follows an existing leaf symlink; subsequent rename replaces the named durable file. ToolBench also writes manifest.json and transcript.json directly (toolbench-session.ts:166 and toolbench-session.ts:231). proven-snapshot-links.ts:54 appends through an existing leaf, and remote-service.ts:288 truncates through one. A pre-existing link can point outside the designated root even if the root itself was canonicalized; the calls shown do not establish the leaf's identity. Some of the final state names may be deliberately persistent, but the code shown does not prove that a pre-existing temp or replaced destination belongs to this process. Suggested fix: use exclusive random temporary files and no-follow/descriptor-bound checks where available, verify existing durable records and parent identity, and refuse or safely quarantine unexpected objects before replacing them.

### F5 — Medium: media retention deletes by namespace and manifest, not full tree ownership

build-user-media.ts:170 accepts digest-shaped directories, validates contained manifest run IDs, age and terminal status, then recursively removes the entire folder and removes the corresponding prepared file (build-user-media.ts:191). The startup callback treats unknown runs as terminal (runner-start.ts:273). Those checks do not establish that every other entry under the folder or the prepared leaf was created by this Runner; the object sweep similarly acts on digest-shaped old unreferenced names (build-user-media.ts:198 and artifact-store.ts:164). Suggested fix: retain a durable owned-object inventory or marker and verify the exact directory/leaf identities before deleting; refuse unexpected entries instead of recursively sweeping them.

### F6 — Medium: extension upload and secret sweeping trust names or age

Uploads use a random ID but writeFile is not exclusive (extension-management-service.ts:290), and prune later removes the recorded path without revalidating the object (extension-management-service.ts:1304). The MCP secret sweep stats and removes every aged directory entry, not only names it created (extension-mcp-launcher.ts:79); its generated launcher claims any .secret entry using a PID-suffixed rename that can replace an existing claimed name, then removes that name (extension-mcp-launcher.ts:23). Launcher repair replaces a digest-named existing file whose bytes do not match (extension-mcp-launcher.ts:51). These are extension-home paths, but name, age and memory records alone do not prove ownership of a replaced file. Suggested fix: create exclusively, retain and verify object identity, restrict sweeping and claims to validated owned secret records, and refuse unexpected replacement files.

### F7 — Medium: extension staging and discovery cleanup can remove unproven directories

extension-sources.ts:211 creates random scratch with recursive mkdir and always removes it (extension-sources.ts:239); extension-package-store.ts:48 similarly constructs staging and removes it in finally (extension-package-store.ts:64). Their random names make accidental collisions unlikely, but recursive mkdir does not prove the directory was newly created. Package collection removes digest-shaped, unretained directories (extension-package-store.ts:82), and chmod/removal recursively walk those contents (extension-package-store.ts:284); lstat avoids intentionally following a symlink leaf, but the name and retention set do not prove each entry and the checks are separate from the later mutations. MCP installation uses recursive mkdir then removes the derived root on failure (extension-mcp.ts:319); its discovery finally removes state/builds/{random-run} even if failure occurred before creation (extension-mcp.ts:402 and extension-mcp.ts:425). Suggested fix: create staging roots exclusively, record their identities, verify the same objects before recursive cleanup, and use durable ownership/retention evidence for collection. Fail closed on an unexpected pre-existing root or changed child.

### F8 — High: registry lock and temporary cleanup lack stable ownership

The stale lock path is removed after an age check and a PID-not-found check (extension-registry.ts:580); the path can change between observation and rm, and the release closure recursively removes the path without checking that it still owns the same lock (extension-registry.ts:587). A successor's lock could be removed after replacement. Separately, writeDurable always removes its random temporary path in finally even if open(..., wx) failed before creating it (extension-registry.ts:383). The non-durable writer uses ordinary writeFile on its random temp and can replace an existing target with rename (extension-registry.ts:568). Suggested fix: use an ownership token plus stable identity and race-safe reclamation/release, never remove on failed exclusive creation, and create all temps exclusively while tracking successful creation.

### F9 — Medium: launcher stale and peer-key cleanup lacks object identity

clearStaleInstance holds launcher locks and verifies an instance if one exists, but if no instance record exists it still reads and unlinks launcher-control.key by fixed name (launcher-instance.ts:384). Publishing an instance replaces the fixed record by rename (launcher-instance.ts:363). Peer key creation unlinks a kind's existing key before writing a new one (launcher.ts:814); exit cleanup removes keys for fresh kinds even when a different current peer record was retained (launcher.ts:637). Those operations do not prove that the file being unlinked or replaced is the object for the instance being cleaned up. Suggested fix: bind records and keys to instance IDs and a verified file identity, and refuse removal or replacement if the matching record or ownership token is absent or changed.

### F10 — Low: durable names and created temporary paths are not pinned through removal

Migration serializes through its SQLite lock and verifies journal/pointer state before journal removal (credential-migration.ts:75, credential-migration.ts:140 and credential-migration.ts:175). writeAtomicJson then replaces the named journal/pointer and removes a created random temp (credential-migration.ts:374). The destination and journal are not revalidated by file identity immediately at rename/removal, so the process does not prove that a replaced path is the same object it verified. Similarly, storage-key.ts:39 and storage-key.ts:54, launcher-instance.ts:311 and launcher-instance.ts:314, launcher.ts:793 and launcher.ts:795, and remote-device-store.ts:340 and remote-device-store.ts:351 select a temp this process created, but do not recheck its identity at unlink if another actor replaces the pathname. Suggested fix: retain and revalidate verified record and temp identities under the applicable lock, refuse unexpected replacements, and keep temp cleanup conditional on successful exclusive creation.

### F11 — High: failed device initialization can remove a pre-existing key

writePrivateExclusive treats EEXIST from linkSync as success without reporting whether it published the key (remote-device-store.ts:335). If the later identity save fails, ensure unconditionally unlinks this.keyPath (remote-device-store.ts:128 and remote-device-store.ts:140), including the case where that key predated this attempt. If the save succeeds after EEXIST, the newly generated public key can instead be recorded alongside the old private key; the mismatch is detected only when the key is used (remote-device-store.ts:324). Rotation has a similar cleanup of its random key name after save failure (remote-device-store.ts:201); it also deletes the old key and session by record-derived/fixed names under its owner lock (remote-device-store.ts:198 and remote-device-store.ts:204). Owner-lock release unlinks its fixed record name without verifying the same record is still there (remote-device-store.ts:258 and remote-device-store.ts:266). The lock and validated key filename do not by themselves pin the actual file. Suggested fix: return a creation/identity receipt from exclusive publication, verify the key pair before publishing an identity, only remove an object proven to be created by this attempt, and verify identity for rotation, logout and owner-record cleanup before unlinking.

### F12 — Medium: uninstall rewrites user files and removes name-selected install data

self-update.ts:456 reads each user profile and replaces it with a copy with the marked block removed; it blindly unlinks home/.config/fish/conf.d/aiboard.fish (self-update.ts:464). These are user paths outside the managed install; the profile parent/leaf is not canonicalized or ownership-pinned, and the fish filename alone does not prove this install created it. The updater also removes old release-looking or aged staging names (self-update.ts:301), and the install failure handler removes staging even when fresh extraction may have failed before creating it (self-update.ts:383). Uninstall recursively removes versions/bin and optional data paths (self-update.ts:434 and self-update.ts:567); its deferred Windows script can remove the whole install root when state removal was requested (self-update.ts:519). The install lock protects cooperating lifecycle operations but does not prove every pre-existing entry is owned. Suggested fix: verify an installer-owned marker or exact file identity before deleting the fish file, safely update profile content with parent/leaf revalidation, exclusively create staging and track its identity, and restrict recursive cleanup to a verified install/state inventory while retaining unknown files.

**Follow-up (2026-10-31):** `self-update.ts` uses read-only `realpath` and `lstat` checks with its existing `writeFile`, `rename`, `unlink`, `mkdir`, `rmdir` and `rm` mutation APIs. For profiles under the resolved home, it requires a regular leaf containing the installer's exact block, rechecks file identity and content, and rewrites through an exclusively created same-directory temporary file. For fish, it confines the resolved parent to the home and removes only a regular leaf matching the installer's exact template; otherwise it reports that the file was kept. Update staging is created non-recursively, failure cleanup requires creation by that attempt and a matching directory identity, and automatic age-based cleanup of unowned staging names is discontinued. The requested cases are covered in `runner-v2/test/self-update.test.ts`; tests were not run in this change.

This is proportional hardening, not a complete ownership inventory: the profile/fish checks and later rename/unlink and the staging identity check and removal are not descriptor-pinned against concurrent replacement, and the existing recursive version/bin/data and deferred Windows-root cleanup still trust the known install layout. Those residual F12 limitations remain tracked.

The test tripwire was not run, per request. The report cleanup source changed concurrently during this review; F3 records the version observed after that change and is not an approval of the unfinished fix.


## Resolution (coordinator, 2026-10-31)

The review above classifies 23 modules as class 3 mainly because of F1/F2: the startup checks that keep Runner state and the extension home out of the project compared paths lexically. Their intended targets are Runner-owned stores.

- **F1/F2 fixed.** `runner-start.ts` `isInsideProject` now refuses a state directory or extension home that resolves into the project lexically *or* through a symlink or junction, using the real path of the nearest existing ancestor. `remote-home-start.test.ts` "state or extension store linked into the project is refused without --remote" covers both. On the previous source the Runner started with state inside the project instead of refusing. Remote-only nested state is a deliberate product mode (Remote can be granted a broad folder); its owned roots are protected from Remote tools, as before.
- **F3 fixed.** `delivery-execution.ts` report cleanup resolves the report's parent canonically and removes only a regular file inside the run-owned verification workspace (`delivery-report-cleanup.test.ts`). The check-then-remove gap is accepted for this best-effort residue cleanup; failure leaves the file in place.
- **Listed.** With the roots canonically confined, the state and extension-home writers, plus `delivery-execution.ts` and `self-update.ts`, are added to `privateOwners` with one-line justifications. The read-handle owners `remote-artifact-transfer.ts` and `remote-connector.ts` are added to `readHandleOwners`. The audit test passes.
- **Follow-ups (ownership hardening inside Runner-owned roots, not project confinement):**
  - F8, extension registry lock: scheduled next.
  - F11, device key removal after a failed save: high, a real data-loss path for the Remote device identity.
  - F4, fixed temp leaves: low once roots are canonical, since only the local user can plant links in private state.
  - F5, F6, F7, F9, F10 and F12: medium/low; tracked here.
