# Runner V2 filesystem owner review — 2026-11-18, CW3 (CLI worker detection and the Test button)

Scope: the new module `runner-v2/src/cli-worker-detection.ts` and the transient run binding it uses through `cli-worker-processes.ts` (a new target of `execution-host.ts`, below) (packet CW3 of `docs/plans/2026-11-14-cli-workers.md`, §3.2 and §3.4). Source references are relative to `runner-v2/src/`. This is a static review of the change, not a sandbox. The regression coverage is in `runner-v2/test/control-server-cli-workers.test.ts`. The entry in `runner-v2/test/filesystem-mutation-routing.test.ts` refers to this record.

Why it writes: the free checks and the Test must run from folders the Runner owns, never a worktree or a project folder. On Windows VF2's lookup searches its own folder before PATH, so a `claude.cmd` or `codex.exe` committed at a repository's root would otherwise shadow the real CLI (CW2's lookup note). The Test runs a CLI in an empty folder (§3.4), and Codex and agy read the result schema from a file.

| Module | Mutation-capable imports | Classification | Targets and derivation | Evidence | Concerns |
| --- | --- | --- | --- | --- | --- |
| cli-worker-detection.ts | mkdir, rm, writeFile (`node:fs/promises`); readFile is a read | 3: fixed Runner-private folders under the state directory | (a) `<state>/cli-workers/lookup`, created with `mkdir` (recursive, 0700) before each free check. (b) Per Test, `<state>/cli-worker-tests/<16 hex>/` from `randomBytes(8)`, with an empty `work/` folder (the CLI's working folder) created the same way. (c) `<that folder>/result.schema.json`, written with `writeFile` (0600) from `cliWorkerResultSchemaJson()`, for Codex and agy only. (d) `rm` (recursive, force) of exactly that Test folder in the Test's `finally`. `<state>` is the Runner's state directory (runner-start.ts), which startup already refuses inside the project. No path component comes from a request, the home or a CLI; the provider id that selects a CLI is checked against `CLI_WORKER_PROVIDER_IDS` before anything runs. | The Test folder is removed only when no process ran in it (its process session never opened) or when the session's stop was proven: `keepFolder` turns true as soon as the session opens and false again only after `CliWorkerProcessSession.close()` resolved, which is `ManagedProcessService.closeAgent` for the session's owner and then the run binding's own verified close (cli-worker-processes.ts). A start or read that throws still goes through that close first. When the stop is not proven, the folder is kept and the Test reports `timed_out`, so nothing is deleted from under a process that may still run there. A failed `rm` (a Windows handle held a moment longer) is logged and the folder stays; the Test's result stands. Codex's `-o` file is written by Codex itself inside the Test folder; the Runner only reads it. | (a) The Runner writes nothing into the lookup folder, but the free probes run with it as their working folder, so a CLI's own probe could leave a file there. The lookup refuses a CLI found in that folder itself (CW2's backstop), so such a file can never be launched as the CLI. (b) A Test folder kept after an unverified stop, or after a Runner crash during a Test, is not swept yet: no residue cleanup knows `state/cli-worker-tests`. It holds only the schema, Codex's result file and whatever the CLI wrote in `work/` in plan or read-only mode. The sweep, which may delete a folder only after proving no process of its run binding is alive, is a follow-up (plan §3.4). (c) `rm` is recursive on a Runner-built random folder; a CLI in its most restricted mode could still create a link inside `work/`. `rm` with `recursive` removes links themselves, not their targets. |
| execution-host.ts (the transient binding only) | mkdir, rm, readdir, truncate (`node:fs/promises`) | 3: a fixed Runner-private folder under the state directory | `<state>/transient-runs/<runId>/`, created with `mkdir` (0700, not recursive, so an existing folder is refused) when `bindRun` gets `transient: true`. `<runId>` is `cli-worker-{check,test}-<12 hex>` from `randomBytes(6)` (cli-worker-processes.ts), checked by `safeSegment` like every run id. Inside it the binding's run root (`runtime/`), a private `ManagedProcessService` record store (`managed/`), a private Windows Job host (`job-host/`, its process records and each process's `stdout.log`/`stderr.log`, with no spares) and an `ArtifactStore` (`artifacts/`) replace the shared `<state>/builds/<runId>`, `<state>/managed-processes`, `<state>/managed-processes-job-host` and host artifacts. The shared Job host never deletes a released process's record or logs, and a CLI's `auth status` prints account fields, so its output must not land there. `rm` (recursive, force) of exactly that folder. | The folder is removed only after the binding's own `close()` resolved, which throws unless every managed process of the run was proven stopped and the run's stores closed; then the private record store is closed and the folder removed. A construction that rolled back completely (nothing started) removes it the same way. Before the `rm`, the release waits for the private Job host's supervisor processes to exit (`awaitSupervisorsExited`: a read-only 25 ms poll of the PIDs its records name, up to 15 s; on an idle PC they had all exited already), since a released process's supervisor holds its output logs until it exits. The `rm` then retries briefly. If it still fails, every file under the folder is emptied (`truncate`) and removed where it can be, and the warning names the folder, any supervisor still running and every file that could be neither, so a CLI's output is never left there unnoticed; the stop stands. A construction that rolled back completely removes the folder the same way. The wrapper's close is memoized, so the session's close and the host's never race two removals. The host's own close, and a host closed while the binding was being built, close the transient wrapper, so they remove the folder after a proven stop too. A close that throws or a Runner crash keeps the folder. | (a) A kept folder may hold a managed record still marked running, with no recovery owner: nothing reopens `transient-runs` at startup. It may also hold the CLI's raw output, account fields included, until it is swept: the price of never deleting from under a process whose stop was not proven. It is residue for the same follow-up sweep as kept Test folders, which may delete only after proving no process of that run is alive. (b) Without this binding a check or Test would add its records to the shared store for good: the store refuses new starts at 4096 records and the Runner refuses to start above it, and every Build's processes share it. |

`cli-worker-processes.ts` (new in CW3) imports no `node:fs` API: it opens execution-host run bindings and calls `ManagedProcessService`, whose files are their own reviewed owners. `cli-worker-adapters.ts` (CW2) imports only `stat`, a read. The control-server routes and the Build manager's `providerTestPassed` write no file: the Test result goes to the home through `applyHomeBatch` (aiboard-home-store.ts, reviewed 2026-11-12), and the cooldown's end is a scheduler event (sqlite-scheduler-store.ts).
